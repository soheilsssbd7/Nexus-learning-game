## فاز ۰ — راه‌اندازی پروژه (تخمین: ۱ روز)

### تسک ۰.۱ — ایجاد ریپازیتوری
ریپازیتوری گیت‌هاب جدید بساز با نام `nexus-game`. `.gitignore` مخصوص Godot 4 اضافه کن (شامل `.godot/`, `*.import`, `export_presets.cfg` اگر حاوی کلید امضا باشد). `README.md` اولیه با توضیح یک‌خطی پروژه، لینک به `docs/00-START-HERE.md`، و نسخه‌ی Godot موردنیاز.
**✅ DoD:** `git log` یک commit اولیه دارد؛ `git clone` تازه، پوشه‌ی خالی صحیح می‌دهد.

### تسک ۰.۲ — ساخت پروژه‌ی Godot
پوشه‌ی `game/` بساز، از Godot 4.6+ یک پروژه‌ی جدید با نام `NEXUS` بساز. تنظیمات `project.godot`:
- Display: `window/size/viewport_width=1080`, `window/size/viewport_height=1920` (عمودی، موبایل‌محور)
- Stretch mode: `canvas_items`, aspect: `expand`
- Rendering: Mobile renderer (نه Forward+) برای سازگاری با گوشی‌های ارزان
- Input Map: اکشن‌های `drag_start`, `drag_end` (اگرچه لمس/موس عمدتاً مستقیم در کد هندل می‌شود)

**✅ DoD:** پروژه در ادیتور باز می‌شود؛ صحنه‌ی خالی روی دستگاه/شبیه‌ساز اجرا می‌شود.

### تسک ۰.۳ — ساختار پوشه‌ها
دقیقاً طبق درخت پوشه‌ی بخش ۲ سند `01-ARCHITECTURE.md` تمام دایرکتوری‌ها را بساز (با فایل `.gitkeep` در پوشه‌های خالی).
**✅ DoD:** ساختار پوشه با سند معماری ۱۰۰٪ مطابقت دارد.

### تسک ۰.۴ — نصب GUT (فریمورک تست)
افزونه‌ی GUT را در `game/addons/gut/` نصب و در Project Settings فعال کن. یک تست نمونه‌ی خالی بنویس تا نصب صحیح تأیید شود.
**✅ DoD:** اجرای `gut` از خط فرمان (headless) بدون خطا، یک تست PASS شده گزارش می‌دهد.

### تسک ۰.۵ — تنظیم CI پایه
`.github/workflows/ci.yml` بساز: روی هر push/PR، پروژه‌ی Godot را headless باز کند، تست‌های GUT را اجرا کند، و در صورت شکست، PR را fail کند.
**✅ DoD:** یک PR آزمایشی باز می‌شود و CI سبز/قرمز صحیح گزارش می‌دهد.

## فاز ۱ — هسته‌ی معماری و Autoload‌ها (تخمین: ۲-۳ روز)

### تسک ۱.۱ — EventBus
`scripts/autoload/EventBus.gd` بساز؛ یک autoload خالی که فقط سیگنال تعریف می‌کند (الگوی Signal Bus)، از جمله:
```gdscript
signal orb_placed(orb_data: Dictionary)
signal balance_changed(left_weight: float, right_weight: float)
signal level_completed(level_id: String, stats: Dictionary)
signal error_detected(error_type: String)
signal hint_requested(hint_id: String)
```
در `project.godot` به‌عنوان Autoload با نام `EventBus` ثبت کن.
**✅ DoD:** از یک اسکریپت تست، `EventBus.orb_placed.emit(...)` بدون خطا کار می‌کند.

### تسک ۱.۲ — PlayerModel (کلاس داده)
`scripts/data/PlayerModel.gd` را دقیقاً مطابق اسکیمای بخش ۲ در `03-DATA-SCHEMAS.md` به‌صورت `class_name PlayerModel extends Resource` با `@export var` برای هر فیلد بساز. متد `to_dict()` و `static func from_dict(d: Dictionary) -> PlayerModel` اضافه کن.
**✅ DoD:** تست GUT: یک PlayerModel بساز، به dict تبدیل کن، دوباره بساز، برابری فیلدها تأیید شود.

### تسک ۱.۳ — SaveSystem
`scripts/autoload/SaveSystem.gd` (autoload): متدهای `save_player_model(model: PlayerModel)` و `load_player_model() -> PlayerModel`. مسیر ذخیره: `user://player_model.save` به فرمت JSON. باید `schema_version` را چک کند و اگر قدیمی بود، migration ساده انجام دهد (فیلد جدید = مقدار پیش‌فرض).
**✅ DoD:** تست GUT: ذخیره → بستن و باز کردن مجدد (شبیه‌سازی‌شده) → بارگذاری → داده‌ی یکسان بازمی‌گردد.

### تسک ۱.۴ — GameState
`scripts/autoload/GameState.gd` (autoload): وضعیت نشست فعلی (world فعلی، level فعلی، آیا اولین اجرای بازی است یا نه، ارجاع به PlayerModel فعال).
**✅ DoD:** از صحنه‌ی اصلی قابل خواندن/نوشتن است؛ تست دستی: تغییر `current_level` در یک صحنه، در صحنه‌ی دیگر قابل مشاهده است.

## فاز ۲ — مکانیک هسته‌ی ترازو (تخمین: ۴-۶ روز، مهم‌ترین فاز)

### تسک ۲.۱ — صحنه‌ی WeightOrb
`scenes/gameplay/WeightOrb.tscn` + `scripts/gameplay/WeightOrb.gd`. یک `Area2D` قابل‌درگ (drag) با فیلدهای: `orb_type` (enum: `NUMBER`, `GHOST`, `NEGATIVE`)، `value: float`، `is_placed: bool`. رویدادهای `_input_event` برای شروع/پایان درگ (هم `InputEventScreenTouch` هم `InputEventMouseButton` را پوشش بده).
**✅ DoD:** یک صحنه‌ی تست دستی: کره را با موس/لمس می‌شود کشید و رها کرد؛ مکان صحیح به‌روزرسانی می‌شود.

### تسک ۲.۲ — صحنه‌ی BalanceScale
`scenes/gameplay/BalanceScale.tscn` + `scripts/gameplay/BalanceScale.gd`. دو `Area2D` به‌عنوان «کفه»‌ی چپ/راست که WeightOrb می‌پذیرند. متد اصلی:
```gdscript
func calculate_tilt() -> float:
    var left_sum := _sum_weights(left_orbs)
    var right_sum := _sum_weights(right_orbs)
    var diff := right_sum - left_sum
    var max_diff := 20.0  # برای نرمال‌سازی زاویه
    return clamp(diff / max_diff, -1.0, 1.0) * MAX_TILT_ANGLE_DEG
```
با Tween، `rotation_degrees` بازوی ترازو را نرم به سمت `calculate_tilt()` انیمیت کن (نه پرش ناگهانی). هر بار تغییر وزن، `EventBus.balance_changed` را emit کن.
**✅ DoD:** تست GUT برای `calculate_tilt()` با چند سناریوی وزن مختلف؛ تست دستی: قرار دادن کره‌ها به‌صورت بصری ترازو را کج/صاف می‌کند.

### تسک ۲.۳ — GhostOrb (کره‌ی روح)
`scripts/gameplay/GhostOrb.gd` که از `WeightOrb` ارث‌بری می‌کند، فیلد `hidden_value` (فقط داخلی، هرگز در UI نمایش داده نمی‌شود تا حل نشود) اضافه می‌کند. طبق `02-ART-BIBLE.md` بخش ۶، ظاهر همیشه رنگ Ghost Violet با آیکون «؟» محو-پررنگ‌شونده.
**✅ DoD:** تست دستی: کره‌ی روح روی ترازو گذاشته می‌شود، وزن واقعی‌اش در محاسبه‌ی تعادل لحاظ می‌شود اما در UI نمایش داده نمی‌شود.

### تسک ۲.۴ — NegativeOrb (حباب ضد-وزن)
`scripts/gameplay/NegativeOrb.gd`: مقدار منفی، در محاسبه‌ی `_sum_weights` کم می‌کند. جلوه‌ی بصری: حرکت آهسته‌ی رو‌به‌بالا وقتی روی کفه نیست (طبق Art Bible بخش ۶).
**✅ DoD:** تست GUT: افزودن NegativeOrb به یک کفه، مجموع وزن آن کفه را کاهش می‌دهد.

### تسک ۲.۵ — تشخیص وضعیت برد (Win Detection)
در `LevelController.gd` (`scripts/gameplay/LevelController.gd`): هر بار `balance_changed` emit شد، چک کن آیا `abs(left_sum - right_sum) <= level.tolerance` است. اگر بله، `EventBus.level_completed` را با آمار جلسه (زمان، تعداد تلاش، راهنمای استفاده‌شده) emit کن.
**✅ DoD:** تست GUT: سناریوی برد شبیه‌سازی‌شده، سیگنال `level_completed` با payload صحیح emit می‌شود.

### تسک ۲.۶ — بازبینی و پلی‌تست دستی فاز ۲
یک سطح hardcoded تستی (بدون سیستم JSON هنوز) بساز: `3 + 5 = ?` با کره‌های ۱، ۲، ۵. به‌صورت دستی بازی کن.
**✅ DoD (Checkpoint فاز):** مکانیک هسته کاملاً قابل‌بازی، smooth، و بدون باگ محسوس در درگ‌اند‌دراپ است — **این فاز نباید عجولانه رد شود چون کل بازی روی این مکانیک بنا می‌شود.**

## فاز ۴ — موتور دشواری و مدل بازیکن (تخمین: ۳-۴ روز)

### تسک ۴.۱ — SkillRating
`scripts/data/SkillRating.gd`: دقیقاً کد بخش ۳ در `03-DATA-SCHEMAS.md` را پیاده‌سازی کن.
**✅ DoD:** تست GUT با چند سناریوی برد/باخت، مقدار Elo طبق فرمول تغییر می‌کند.

### تسک ۴.۲ — ErrorClassifier
`scripts/ai/ErrorClassifier.gd`: با گرفتن state فعلی ترازو (چه کره‌هایی کجا هستند) و state هدف، نوع خطا را طبقه‌بندی کند:
- `wrong_operation`: بازیکن جهت را اشتباه گرفته (اضافه کرده به‌جای کم‌کردن)
- `sign_flip_on_subtraction`: علامت اشتباه در استفاده از NegativeOrb
- `forgets_both_sides`: فقط یک طرف را تغییر داده وقتی باید هر دو طرف تغییر کند
- `computation_error`: جهت درست ولی مقدار عددی اشتباه
- `idle`: بدون حرکت به مدت مشخص (نه یک خطای واقعی، از HintTimingSystem می‌آید)

منطق باید کاملاً rule-based باشد (مقایسه‌ی state فعلی با ساختار مورد انتظار سطح)، **بدون هیچ فراخوانی هوش مصنوعی**.
**✅ DoD:** تست GUT برای هر ۴ نوع خطای غیر-idle با سناریوهای دستی.

### تسک ۴.۳ — HintTimingSystem
`scripts/ai/HintTimingSystem.gd`: تایمر idle (پیش‌فرض ۴۵ ثانیه بدون حرکت) + شمارنده‌ی تلاش ناموفق. وقتی آستانه رد شد، `EventBus.hint_requested` را با `hint_id` مناسب از `level.hint_sequence` emit کن.
**✅ DoD:** تست دستی: بی‌حرکتی ۴۵ ثانیه‌ای، سیگنال hint را صحیح trigger می‌کند؛ ۳ تلاش ناموفق پشت‌سرهم هم همین‌طور.

### تسک ۴.۴ — اتصال DifficultyEngine به LevelLoader
`scripts/autoload/DifficultyEngine.gd`: بعد از هر `level_completed`، رتبه‌ی مهارت مرتبط با `concept_tags` آن سطح را به‌روزرسانی کن (با وزن‌دهی بر اساس `hints_used` طبق نکته‌ی بخش ۳ سند Data Schemas)، سپس به `LevelLoader` بگو سطح بعدی را بر اساس نزدیک‌ترین `difficulty_elo` به رتبه‌ی فعلی بازیکن انتخاب کند (نه صرفاً ترتیب خطی فایل‌ها).
**✅ DoD:** تست یکپارچه: بازیکن شبیه‌سازی‌شده با عملکرد ضعیف، سطوح ساده‌تر بعدی می‌گیرد؛ با عملکرد قوی، پیچیده‌تر.

## فاز ۷ — تولید محتوا (تخمین: ۵-۷ روز)

### تسک ۷.۱ تا ۷.۴ — نویسندگی سطوح Tier 2 تا Tier 5
طبق ساختار بخش ۴ سند GDD اصلی (تفریق/منفی → متغیر مجهول → دومجهولی → مسئله‌ی کلامی)، هر Tier حدود ۸ تا ۱۲ سطح، با دشواری تدریجی داخل خودِ Tier. هر سطح باید یک `narrative_intro` منحصربه‌فرد داشته باشد که با روایت کلی هماهنگ باشد (تسک ۷.۵).
**✅ DoD هر Tier:** تمام سطوح آن Tier از ابتدا تا انتها قابل‌حل‌اند؛ منحنی دشواری داخل Tier یکنواخت افزایشی است (نه پرش ناگهانی).

### تسک ۷.۵ — اسکریپت روایت
`data/narrative/story_beats.json`: قوس داستانی کامل «عدم‌تعادل بزرگ» طبق GDD اصلی — صحنه‌ی افتتاحیه، ۳ نقطه‌ی عطف میانی (یکی در ورود به هر Tier جدید)، و پایان‌بندی در Summit of Equilibrium. هر بیت شامل متن + اشاره به کدام دارایی هنری محیطی (بخش ۵ Art Bible) لازم است.
**✅ DoD:** خواندن کامل روایت، یک داستان منسجم ۲-۳ ساعته می‌سازد (نه فقط جملات پراکنده).

### تسک ۷.۶ — AudioManager و لیست دارایی صوتی
`scripts/autoload/AnalyticsManager.gd`-مانند: `scripts/autoload/AudioManager.gd` برای پخش موسیقی/SFX. لیست دارایی موردنیاز برای سفارش/تولید:
- SFX: برداشتن کره، رهاکردن کره، جیرجیر کج‌شدن ترازو، زنگ موفقیت جزئی، صدای باز شدن دروازه، صدای Aria (غیرکلامی — بوق/زنگ ملایم نه گفتار)
- موسیقی: تم Hub (آرام)، تم هر Tier (۵ تِم متمایز اما هم‌خانواده)، استینگر پیروزی سطح، استینگر پایان بازی
**✅ DoD:** حداقل نسخه‌ی placeholder هر مورد در بازی integrate و قابل‌شنیدن است.

## فاز ۹ — بک‌اند و همگام‌سازی (تخمین: ۳-۴ روز، می‌تواند از هفته‌ی ۴ موازی شروع شود)

### تسک ۹.۱ — راه‌اندازی پروژه‌ی بک‌اند
`backend/`: `npm init`، نصب `express`, `pg`, `typescript`, `zod` (برای validation). ساختار طبق بخش ۲ سند Architecture.
**✅ DoD:** `npm run dev` سرور را روی پورت محلی بالا می‌آورد، `GET /health` پاسخ ۲۰۰ می‌دهد.

### تسک ۹.۲ — اسکیمای دیتابیس
`backend/src/db/schema.sql` دقیقاً طبق بخش ۶ سند Data Schemas اجرا شود؛ اسکریپت migration ساده بساز.
**✅ DoD:** جداول در یک Postgres محلی/Docker با موفقیت ساخته می‌شوند.

### تسک ۹.۳ — Endpoint همگام‌سازی مدل بازیکن
`POST /api/player-model/:id/sync` و `GET /api/player-model/:id`. اعتبارسنجی payload با `zod` طبق اسکیمای بخش ۲ Data Schemas.
**✅ DoD:** تست یکپارچه (`backend/test/playerModel.test.ts`): ارسال یک مدل نمونه، دریافت مجدد آن، تطابق کامل.

### تسک ۹.۴ — Endpoint رویدادها
`POST /api/events` طبق اسکیمای بخش ۵ Data Schemas؛ فقط insert، بدون منطق پیچیده در MVP.
**✅ DoD:** رویداد نمونه ارسال، در جدول `events` قابل‌مشاهده است.

### تسک ۹.۵ — احراز هویت ساده‌ی دستگاه (بدون PII)
`backend/src/middleware/deviceAuth.ts`: هر نصب یک `device_token` تصادفی محلی تولید و نگه می‌دارد (نه ایمیل/رمز عبور — کودکان حساب نمی‌سازند).
**✅ DoD:** درخواست بدون توکن معتبر رد می‌شود (۴۰۱)؛ با توکن معتبر عبور می‌کند.

### تسک ۹.۶ — NetworkClient در Godot
`scripts/autoload/NetworkClient.gd`: `HTTPRequest` wrapper با صف آفلاین (Offline Queue) — اگر اتصال نبود، رویدادها/همگام‌سازی محلی صف می‌شوند و به‌محض اتصال، به‌ترتیب ارسال می‌شوند.
**✅ DoD:** تست دستی: قطع اینترنت شبیه‌سازی‌شده، بازی بدون کرش ادامه می‌یابد؛ با وصل‌شدن مجدد، صف خالی می‌شود.

## فاز ۱۰ — QA، آنالیتیکس و Build (تخمین: ۳-۵ روز)

### تسک ۱۰.۱ — تکمیل پوشش تست GUT
حداقل یک تست برای هر فایل در `scripts/data/`, `scripts/ai/` (منطقی، نه UI). هدف: منطق‌های حیاتی (محاسبه‌ی وزن، Elo، طبقه‌بندی خطا، ذخیره/بارگذاری) ۱۰۰٪ پوشش داده شوند.
**✅ DoD:** `gut` headless بدون fail اجرا می‌شود؛ گزارش پوشش تولید شود.

### تسک ۱۰.۲ — پروتکل پلی‌تست کودکان
یک سند کوتاه (`docs/playtest-protocol.md`) بنویس: ۵ کار مشخص که یک کودک ۹-۱۲ ساله بدون راهنمایی بزرگسال باید بتواند انجام دهد (مثلاً «بدون کمک، سطح اول را کامل کن»)؛ چک‌لیست مشاهده برای مسئول تست (کجا گیر کرد؟ کجا خندید؟ کجا Aria را نادیده گرفت؟).
**✅ DoD:** سند آماده‌ی استفاده در جلسه‌ی واقعی پلی‌تست است.

### تسک ۱۰.۳ — AnalyticsManager
`scripts/autoload/AnalyticsManager.gd`: تمام ۶ رویداد حداقلی (بخش ۵ Data Schemas) را در نقاط صحیح کد trigger کن و به `NetworkClient` بفرست.
**✅ DoD:** یک جلسه‌ی کامل بازی، تمام رویدادهای مورد انتظار را در جدول `events` بک‌اند ثبت می‌کند.

### تسک ۱۰.۴ — تنظیمات Export اندروید
`export_presets.cfg`: نام پکیج (`com.<studio>.nexus`)، حداقل SDK متناسب با پوشش گوشی‌های ارزان (API 24+ طبق توصیه‌ی معماری)، آیکون، مجوزهای حداقلی (فقط اینترنت — **بدون** دسترسی به مخاطبین/موقعیت/دوربین که برای این بازی غیرضروری‌اند).
**✅ DoD:** ساخت یک APK امضاشده با موفقیت روی حداقل یک دستگاه واقعی ارزان‌قیمت نصب و اجرا می‌شود.

### تسک ۱۰.۵ — Smoke Test نهایی فاز
چک‌لیست: نصب تازه → Onboarding → تکمیل ۳ سطح اول → مشاهده‌ی Aria حداقل یک‌بار → باز کردن Parent Dashboard → بستن و بازکردن مجدد اپ (پایداری save).
**✅ DoD:** تمام موارد بدون کرش یا رفتار غیرمنتظره عبور می‌کنند.

## تعریف کلی «انجام‌شدن MVP»

MVP وقتی کامل است که همه‌ی این‌ها هم‌زمان برقرار باشد:

- [ ] تمام ۵ Tier با مجموع حدود ۴۰-۶۰ سطح قابل‌بازی و قابل‌حل هستند
- [ ] Aria در تمام سناریوهای خطا/idle به‌درستی و بدون افشای جواب مستقیم واکنش نشان می‌دهد
- [ ] بازی کاملاً آفلاین قابل‌بازی است؛ همگام‌سازی فقط هنگام اتصال اتفاق می‌افتد
- [ ] Parent Dashboard داده‌ی واقعی و دقیق نمایش می‌دهد
- [ ] APK امضاشده روی حداقل ۲ مدل گوشی متفاوت (یکی قدیمی/ارزان) تست شده
- [ ] حداقل یک دور پلی‌تست واقعی با کودکان انجام و بازخورد اعمال شده
- [ ] هیچ داده‌ی PII در کلاینت یا بک‌اند ذخیره نمی‌شود

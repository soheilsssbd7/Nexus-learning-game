### ADR-001 — قفل نسخه‌ی Godot
**زمینه:** `00-START-HERE.md` می‌گوید آخرین 4.x پایدار (حداقل 4.6) و نسخه را در README قفل کن؛
در زمان اجرا (سپتامبر ۲۰۲۶) آخرین stable روی GitHub **4.7.2-stable** (۱۸ اوت ۲۰۲۶) است.
**تصمیم:** همه‌جا (README، CI، `tools/setup-godot.sh`، `config/features`) روی `4.7.2-stable` قفل می‌شود.
**پیامد:** اگر نسخه‌ی دیگری باز کند، ممکن است `.godot/` و `*.uid` را بازنویسی کند؛ به‌همین‌دلیل
`.godot/` ignore و فایل‌های `.uid` commit می‌شوند. تغییر نسخه = ADR تازه + اجرای کامل CI.

### ADR-002 — workflow تک‌شاخه‌ای
**زمینه:** `01` §۴ «هر تسک = یک PR به `develop`»؛ اما محیط کاری فعلی روی یک شاخه‌ی ثابت
(`arena/01a07efb-nexus-learning-game`) قفل است و ساخت/فشار شاخه‌ی دیگر مجاز نیست.
**تصمیم:** هر تسک = یک commit با پیشوند `[P<phase>.<task>]`؛ پایان هر فاز = یک PR به `main` با
توضیح DoD و لینک run سبز CI. `develop` فعلاً ساخته نمی‌شود (هنگام ورود تیم، فقط یک `git branch`).
**پیامد:** تاریخچه‌ی reviewable حفظ می‌شود؛ ریویو در سطح فاز به‌جای تسک.

### ADR-003 — `*.import` در گیت نمی‌آید
**زمینه:** تسک ۰.۱ خواسته `*.import` را ignore کنیم (Godot 4 رسماً commit کردنش را توصیه می‌کند).
**تصمیم:** طبق سند ignore شد. تمام تنظیمات import که واقعاً مهم‌اند به سطح **project** منتقل شدند
(`textures/vram_compression/import_etc2_astc=true` برای موبایل، stretch، renderer) تا رفتار بین
ماشین‌ها یکسان بماند؛ هر تنظیمِ import-خاصِ لازم در کد/تم انجام می‌شود (نه در فایل `.import`).
**پیامد:** diff تمیز؛ ریسک = اگر روزی «compress mode» خاصِ تکسچری لازم شد، باید override در کد
یا استثنای گیت‌ایگنور ثبت کنیم (با ADR).

### ADR-004 — CI و build اندروید
**زمینه:** `01` §۲ فقط `ci.yml` دارد؛ اما DoD فاز ۱۰ «APK امضاشده روی دستگاه واقعی» است و در این
سندباکس JDK/Android SDK قابل نصب نیست. ریپو خصوصی است → دقیقه‌ی CI محدود.
**تصمیم:** `ci.yml` (import + GUT + gdlint + validate_levels) روی push/PR به `main`/`develop` +
`workflow_dispatch`، با کش باینری و `concurrency`. `android-export.yml` (فاز ۱۰) فقط دستی: نصب
JDK 17 + Android SDK (platform 36, build-tools 36)، دانلود `export_templates.tpz` (۱.۳GB)، export
`--export-release "Android" ... --keystore $KS --keystore-pass "$KS_PASS"`، آپلود AAB/APK به artifact.
`export_presets.cfg` commit می‌شود ولی **فیلدهای رمز خالی**؛ رمزها فقط در GitHub Secrets.
**پیامد:** هیچ رازی در ریپو؛ build واقعی از artifact؛ مصرف CI کنترل‌شده.

### ADR-005 — شناسه‌ی بازیکن و احراز هویت دستگاه
**زمینه:** `03` §۲ نمونه `p_193f2a7e` (غیر-UUID) در برابر `03` §۶ `player_id UUID PRIMARY KEY` → INSERT می‌شکند؛
همچنین `deviceAuth` (تسک ۹.۵) هیچ جدولی برای ذخیره‌ی توکن ندارد.
**تصمیم:** `players.player_id TEXT PRIMARY KEY` با قاعده‌ی `p_<12 hex>` (کلاینت از `UUID.v4()`
برش می‌زند)؛ جدول `device_tokens(device_token TEXT PK, player_id TEXT, created_at, last_seen_at)`؛
هر درخواست با `X-Nexus-Device-Token`؛ توکن نامعتبر = 401. هیچ ستون PII اضافه نمی‌شود.
**پیامد:** DDL بک‌اند با نمونه‌ی سند فرق دارد (این فایل، مرجع اصلاح است)؛ در `backend/src/db/schema.sql`
مستند + مهاجرت شماره‌دار.

### ADR-006 — گسترش اسکیمای سطح (قابل‌طبقه‌بندی‌کردن خطا)
**زمینه:** تسک ۴.۲ خطاها را با «ساختار مورد انتظار» مقایسه می‌کند ولی §1 هیچ expected solution ندارد؛
تسک ۴.۳ آستانه‌ی idle را hardcode می‌کند درحالی‌که trigger داده‌محور است.
**تصمیم:** دو افزوده به §1:
```jsonc
"solution_spec": {                       // اختیاری ولی لازم برای Tier ≥ 2
  "intended": { "right_orbs": [5, 2, 1], "operations": ["add", "add", "add"] },
  "wrong_ops": { "remove_from_left": [5] } // حرکتی که بازیکن «نباید» انجام دهد/نمونه‌ی اشتباه متعارف
},
"tolerance_strategy": "exact" | "range",   // فقط برای خوانایی؛ tolerance عدد مرجع است
```
`HintTimingSystem` رشته‌ی trigger را پارس می‌کند: `idle_<n>s`، `fail_<n>x`، `help_requested`،
`first_wrong_attempt`؛ مقدار پیش‌فرض ۴۵s فقط وقتی سطح هیچ تریگری ندارد.
**پیامد:** `tools/validate_levels.py` این‌ها را چک می‌کند؛ `LevelData.gd` فیلدها را اختیاری می‌گیرد
(سطح بدون `solution_spec` → ErrorClassifier فقط `computation_error`/`idle` می‌دهد، نه ادعای دروغ).

### ADR-007 — خط تولید هنر: برداری/پروسیجرال
**زمینه:** `02` §۱ سبک «Flat Vector + Soft Gradient»، §۸ ترجیح SVG، و A9 (۴۸ ترکیب آواتار).
همچنین سقف حجم ورک‌اسپیس.
**تصمیم:** هنر بازی از این جنس باشد: (الف) SVG برای UI/آیکون‌ها/پس‌زمینه‌های ساده؛
(ب) `Polygon2D`/`CustomDraw2D` + shader برای Aria (ایکوساهدرون + هسته‌ی نورانیِ رنگ‌تغییرکننده) و
ذرات؛ (ج) آواتار = ۳ لایه (پوست/مو/لباس) با `CanvasItem.material` و palette-swap → ۶ تُن × ۸ مو ×
رنگ آزاد بدون هیچ اسپرایت اضافی؛ (د) تصاویر AI فقط مرجع طراحی در `/tmp` (commit نمی‌شوند).
**پیامد:** حجم ریپو پایین، مقیاس‌پذیر روی DPIهای موبایل، بدون آتی‌فکت؛ هزینه = کد رندر بیشتر،
و نیاز به ریویو چشمی human در پایان فاز ۸.

### ADR-008 — صدا
**زمینه:** تسک ۷.۶ لیست SFX/موسیقی را می‌خواهد ولی هیچ منبع صوتی در سندباکس قابل دانلود نیست
(archive.org/freesound مسدود). DoD: «نسخه‌ی placeholder قابل‌شنیدن».
**تصمیم:** `tools/gen_audio_placeholder.py` فایل‌های WAV کوتاه (mono 22.05kHz، ۱۶bit، بدون وابستگی)
تولید می‌کند: SFX برداشتن/رهاکردن/کج‌شدن/موفقیت/دروازه و یک پَد حلقه‌ای Hub. همه از یک
`AudioManager` autoload با ۲ bus (`Music`, `SFX`) و ذخیره‌ی سطح صدا در `user://settings.cfg`.
موسیقی نهایی = دارایی سفارش‌داده‌شده توسط مالک، جایگزینی فقط در فایل (بدون تغییر کد).
**پیامد:** بازی از فاز ۶ صدا دارد؛ حجم placeholder ≤ ۱MB؛ هیچ فایل صوتی حقوق-سردرگم در ریپو نیست.

### ADR-009 — پیکربندی اندروید
**زمینه:** تسک ۱۰.۴ فقط «minSdk 24+» را گفته. Google Play: از ۳۱ اوت ۲۰۲۶ هر اپ/آپدیت جدید باید
**target API 36** (اندروید ۱۶) داشته باشد (تمدید قابل‌درخواست تا ۱ نوامبر)؛ سیاست Families: بدون
تبلیغ شخصی‌سازی‌شده، بدون AAID/IMEI/MAC/location، SDK تأییدشده، privacy policy، Data Safety صادقانه.
**تصمیم:** `minSdk=24`، `targetSdk=36`، `compileSdk=36`، build-tools 36.۰.۰؛ مجوزها فقط
`INTERNET` (sync) و `VIBRATE` (بازخورد لمسی `02` §۷ — `Input.vibrate_handheld`). بدون AdMob، بدون
Crashlytics/Sentry (ADR-010). `keep_screen_on=true` (یادگیری طولانی‌مدت). edge-to-edge و
predictive-back در APK واقعی روی دستگاه چک می‌شود (فاز ۱۰).
**پیامد:** ریسک سازگاری Godot Mobile renderer + API 36 → پوشش با L3؛ حذف هر SDK شخص ثالث = مسیر
انطباق هموار برای «مخاطب کودک».

### ADR-010 — آنالیتیکس بدون SDK
**تصمیم:** `AnalyticsManager` فقط ۶ رویداد §5، batch (هر ۲۰ رویداد یا `session_end`)، حداکثر
۵۰۰ رویداد معوق، backoff نمایی (۵s→۵m، ۵ تلاش)، حذف پس از 2xx؛ crash log **محلی** حلقوی
(`user://logs/crash.log`، ۲۵۶KB) که فقط در Parent Dashboard نشان داده می‌شود، ارسال نمی‌شود.
والد می‌تواند «بهبود تجربه» (sync) را خاموش کند؛ بازی بی‌تغییر کار می‌کند.

### ADR-011 — RTL و i18n
**تصمیم:** همه‌ی متن‌های UI از `tr("KEY")` با فایل‌های `game/locales/fa.csv` + `en.csv` (Godot CSV
translation)؛ پیش‌فرض `fa` و RTL با `layout_direction = LAYOUT_DIRECTION_RTL` روی ریشه‌ی هر صحنه +
`TextServer` BiDi برای متن. عدد درون ترازو/کره‌ها **لاتین** می‌ماند (خوانایی ریاضی) ولی متن فارسی
با ارقام فارسی در روایت/داشبورد — هر دو مسیر در `LocaleFormat.gd` متمرکز است تا یک‌جا عوض شود.
**پیامد:** افزودن زبان = یک CSV؛ ریسک برهم‌ریختگی BiDi در مخلوط عدد/متن → تست خودکار RTL (فاز ۶).

### ADR-012 — پروفایل‌ها
**تصمیم:** MVP تک‌پروفایل در هر دستگاه (`user://profiles/default/`). مسیر save از همان ابتدا
پارامتریک است (`SaveSystem` یک `profile_dir` می‌گیرد) تا افزودن چندپروفایلی فقط یک UI منو باشد.
**تأییدمنتظر=مالک:** اگر کلاس/چندبچه‌ای اولویت است، جابه‌جایی به فاز ۶ (هزینه‌ی کم، همین حالا).

### ADR-013 — تست بدون موتور محلی
**زمینه:** در سندباکس Godot اجرا نمی‌شود (دانلود binary مسدود)؛ DoD چند فاز «پلی‌تست دستی» می‌خواهد.
**تصمیم:** (الف) L2 = CI تنها مرجع «کد Godot درست کار می‌کند»؛ (ب) به‌جای چک چشمی، تست‌های
«playable» نوشته می‌شود که صحنه را با `load()` + `add_child()` بالا می‌آورند و `InputEvent*`
تزریق می‌کنند تا یک سطح واقعی تا `level_completed` پیش برود؛ (ج) تست‌های ریاضی/داده کاملاً
headless و بدون scene. (د) یک اسکریپت `tools/render_shot.gd` در CI رندر ۱۶۸۰×۱۹۲۰ می‌گیرد و به‌عنوان
artifact آپلود می‌کند تا تو با چشم ببینی (بدون بزرگ‌شدن ریپو: imageها commit **نمی‌شوند**).

### ADR-014 — بک‌اند: runtime و DB
**تصمیم:** Node 22 + TS + Express 4 + `pg` + `zod`. تست‌ها با `pg-mem` (بدون داکر در سندباکس) و
همزمان در CI روی Postgres 16 واقعی (service container). اسکریپت `db/migrate.ts` فایل‌های
`migrations/*.sql` را به‌ترتیب شماره اجرا می‌کند. استقرار (Render/Fly/…) = تصمیم مالک؛ API بدون
state و stateless scaling-friendly نوشته می‌شود تا انتقال ارزان بماند.

### ADR-015 — ریاضیات مدل بازیکن (فرض‌های مستند)
```
confidence = clamp(attempts / (attempts + 12), 0, 1)          // ۱۲ تلاش ≈ اعتماد کامل
score      = 1.0 - 0.15*min(hints_used,2) - 0.05*min(extra_attempts,4)   // 0.6..1.0
hint_usage_rate, avg_time_to_solve_sec: EMA(α=0.3)
skill_key  = اولین tag از concept_tags که در SKILL_KEYS باشد (mapping ثابت)
```
`score` در `ErrorClassifier` محاسبه و به `SkillRating.update_elo` داده می‌شود (دقیقاً طبق نکته‌ی §3 سند داده‌ها).
**تأییدمنتظر=مالک:** این‌ها قابل‌تنظیم در `data/balance.json` خواهند بود تا بعد از بتا تیون شوند.

### ADR-016 — رجیستری autoload
**زمینه:** A5 (FeatureFlags غایب) + A6 (AudioManager غایب).
**تصمیم:** ترتیب ثبت در `project.godot` (وابستگی به این ترتیب دارد):
`EventBus → FeatureFlags → Log → GameState → SaveSystem → AudioManager → AnalyticsManager → NetworkClient → LevelLoader → DifficultyEngine`.
هر autoload جدید = ویرایش همین جدول + ADR.

### ADR-017 — فونت و مجوز آن
**تصمیم:** `Vazirmatn-Medium.ttf` + `Vazirmatn-Bold.ttf` (v33.0.3، SIL OFL) + `OFL.txt` + `AUTHORS.txt`
در `game/assets/fonts/`. تم بازی (`game/themes/NexusTheme.tres`) در فاز ۸ همین را به‌عنوان
`default_font` ست می‌کند؛ اندازه‌ی پیش‌فرض گفت‌وگو ۲۴px (`02` §۷).
**پیامد:** تعهد حفظ فایل مجوز در ریپو و در «پکیج فروشگاه» (باید در About/لیستینگ ذکر شود).

### ADR-018 — افزوده‌های ساختاری به درخت سند `01`
`game/themes/` (تم Godot)، `tools/` (اسکریپت توسعه، خارج از بازی)، `game/data/balance.json`
(پارامترهای تیونینگ)، `docs/05..08`. باقی درخت ۱۰۰٪ مطابق §2 سند معماری است (تست ۰.۳ این را چک می‌کند).

### ADR-019 — save: امنیت، نگهداری، حذف
MVP همان JSON ساده‌ی `03` §۲ (بدون PII → ریسک پایین)، `FileAccess` با flag read/write، نوشتن
اتمیک (`*.tmp` → rename)، و یک `SaveSystem.export_for_parent()/delete_all()` برای درخواست حذف.
نسخه‌ی post-MVP: رمز `AESContext` با کلید محلی (نه برای تهدید امنیتی، برای سازگاری ادعای Data Safety).
حفظ log گفت‌وگو: تا ۵۰۰ ورودی، چرخشی — «بدون حذف» طبق §۲ یعنی «تا وقتی والد نگاه می‌کند»، نه تا ابد.

### ADR-020 — parent-gate و شفافیت
پرسش دروازه: ضرب دو عدد دو رقمی با ورودی عددی تصادفی (کودک ۹ ساله در ۵ ثانیه نمی‌زند؛ بزرگ‌سال
۲ ثانیه). سه تلاش غلط → بازگشت به منو (قفل نرم، نه تنبیه). داشبورد: نمودار میله‌ی `elo` (نه برچسب
«ضعیف»)، زمان کل، و `aria_transcript_log` قابل‌اسکرول + لینک بازخورد **متنِ باز، بدون فیلد PII**
(فقط کپی در کلیپ‌بورد یا mailto بدون گیرنده‌ی شخصی) تا فرمِ وبی که داده جمع کند وجود نداشته باشد.

### ADR-021 — GDD بازسازی‌شده
چون GDD اصلی در ریپو نیست، `docs/07-GDD-BALANCE-REALM.md` نوشته می‌شود: پله‌ی آموزشی ۵ Tier با
مفهوم/مکانیک/نمونه‌ی مسئله/معیار تسلط، حلقه‌ی تعادل‌سنجی، قوانین ایمنی Aria، نقشه‌ی روایت، و
حریم‌خصوصیت — همه **استخراج‌شده از `00..04`** و با برچسب «بازسازی ایجنت ← تأییدمالک». هر تسک فاز ۷
به این سند ارجاع می‌دهد؛ اگر GDD واقعیِ تو متفاوت است، فقط §های ۰۷ عوض می‌شود و کد (به‌لطف ADR-006)
دست‌نخورده می‌ماند.

### ADR-022 — مالکیت محاسبه‌ی Elo
**زمینه:** `04` تسک ۴.۴ می‌گوید «DifficultyEngine رتبه را به‌روزرسانی می‌کند» و §۳ سند داده‌ها
فرمول را در `SkillRating.gd` می‌خواهد و وزن‌دهی راهنما را در `ErrorClassifier.gd`.
**تصمیم (بدون تضاد):** `SkillRating.apply_result()` تنها جای محاسبه‌ی عدد است (فرمول §۳ + clamp).
`ErrorClassifier` فقط `weighted_score` را می‌سازد. `DifficultyEngine` **ارکستراسیون** می‌کند:
فراخوانی apply_result، گرفتن delta، انتشار برای Analytics، و انتخاب سطح بعدی.
`PlayerModel` هیچ تصمیمی نمی‌گیرد و فقط نگهداری/سریال‌سازی می‌کند.
**پیامد:** هر سه DoD (۴.۱/۴.۲/۴.۴) با یک تست واحد قابل‌اثبات است و عدد در یک نقطه زندگی می‌کند.

### ADR-023 — convention لاگ و GUT
**زمینه:** GUT 9 با `failure_error_types = [engine, gut, push_error]` هر `push_error()` را «تست fail»
می‌داند؛ پس مسیرهای «خطای مدیریت‌شده» (save خراب، بک‌اند در دسترس نیست، پارس نشدن یک ردیف) نباید
`push_error` کنند.
**تصمیم:** `Log.error` (=push_error) فقط برای چیزی که باید در CI قرمز شود. هر چیز قابل‌بازیابی
`Log.warn` است. `Log.debug` در build ریلیز حذف می‌شود. این قاعده در تست‌ها هم رعایت می‌شود:
اگر تستی عمداً مسیر خطا را راه می‌اندازد و انتظار `push_error` داریم، `assert_push_error` استفاده
می‌شود تا GUT بداند آن خطا منتظره بوده است.
**پیامد:** سیگنال‌های CI معنای دقیقی دارند: قرمز = واقعاً خراب، نه لاگِ_diagنوستیک.

### ADR-024 — رجیستری تدریجی autoload
**زمینه:** `01` §۲ همه‌ی autoloadها را از روز اول فهرست می‌کند؛ یک autoload با فایل غایب،
پروژه را در `--import` می‌شکند (و کل CI را).
**تصمیم:** هر autoload در همان تسکی که فایلش ساخته می‌شود به `project.godot` اضافه می‌شود،
با حفظ **ترتیب ADR-016**. لیست کامل نهایی ۱۰ autoload است؛ تا پایان فاز ۱ پنج‌تای اول ثبت شده.
**پیامد:** هر commit قابل‌اجراست (اصل «main همیشه buildable» در `01` §۴ حفظ می‌شود).

### ADR-025 — قابل‌تشخیص‌بودن CI در محیط‌های بسته
**زمینه:** در این سندباکس (و هر محیط مشابه با allowlist شبکه) نه `gh run view --log`
(`results-receiver.actions.githubusercontent.com`) و نه دانلود artifact
(`*.blob.core.windows.net`) کار می‌کند؛ یعنی شکست CI بدون هیچ پیامی می‌ماند.
**تصمیم:** هر دو job در `ci.yml` در حالت `if: failure()` اجراکننده‌ی
`tools/ci_annotate.py <log>` هستند که خطاهای Godot/GUT را به `::error::` annotation تبدیل
می‌کند. خواندن آن‌ها از API معمولی GitHub ممکن است:
```bash
gh api repos/<owner>/<repo>/commits/$(git rev-parse HEAD)/check-runs --jq '.check_runs[]|{id,name,conclusion}'
gh api repos/<owner>/<repo>/check-runs/<id>/annotations --jq '.[]|"\(.annotation_level) L\(.start_line): \(.message)"'
```
artifact‌ها هم همچنان آپلود می‌شوند (برای انسان با دسترسی عادی).
**پیامد:** حلقه‌ی بازخورد L2 در هر محیطی کار می‌کند؛ هیچ لاگ حساسی منتشر نمی‌شود.

### ADR-026 — دام‌های Godot 4.7 (خروجی واقعی فاز ۱)
این‌ها را gdparse/gdlint **نمی‌گیرند** (تایپ استاتیک ندارند)؛ هر بار که مورد تازه‌ای پیدا شد
به همین فهرست اضافه کن تا تکرار نشود:
1. کلاس جهانی `UUID` وجود ندارد (`Identifier "UUID" not declared`) → شناسه‌ی بازیکن با
   `RandomNumberGenerator` ساخته می‌شود (و `OS.get_unique_id()` به‌دلیل سیاست Families ممنوع).
2. روی typed array مثل `Array[Vector2]` متد `length()` نیست؛ فقط `size()`.
3. `JSON.parse_string()` موقع خطا `ERR_PRINT` می‌کند → GUT آن را «Unexpected Error» و fail
   می‌داند و در logcat دستگاه هم می‌نشیند. برای داده‌ی غیرمطمئن: `JSON.new()` + `parse()` +
   `get_error_message()`.
4. `DirAccess` پوشه را خودکار نمی‌سازد؛ `FileAccess.open` در آن صورت `null` می‌دهد
   (پس هیچ‌وقت بدون `ensure_dir` نوشتن نکن).
5. هر `push_error()` در مسیر «مدیریت‌شده» = تست قرمز (ADR-023).
**دسته‌ی فاز ۲ (خروجی واقعی ۴ دور CI؛ همه در کدِ مکانیک ترازو پیدا شدند):**
6. فرمت تکستی `*.tscn`/`*.tres` کامنت **نمی‌پذیرد** → `Parse Error: Expected '['`. توضیح را در
   اسکریپتِ کنار صحنه بنویس، نه داخل صحنه.
7. `Color.lighten()` وجود ندارد؛ `Color.lightened()` است (gdparse نمی‌گیرد).
8. `Color.to_linear()` هم وجود ندارد → تبدیل sRGB→linear را خودت بنویس (تست کنتراست WCAG با
   `get_luminance()` خام عدد ~۴.۰۸ می‌دهد و قانون §۲ را اشتباه رد می‌کند).
9. `const X := preload("...")` اگر preload بشکند پیامش گمراه‌کننده است («Cannot infer the type of
   constant»)؛ `const X: PackedScene = preload(...)` بنویس تا خطای واقعیِ خودِ صحنه بیاید.
10. `_exit_tree()` با **هر** `remove_child` زده می‌شود؛ وضعیت درگ را آنجا ریست نکن — reparent وسط
    درگ باعث شد `end_drag()` بی‌صدا برگردد و `drag_ended` هرگز emit نشود (۶ تست قرمز).
11. `add_child` روی نودی که والد دارد = `push_error` (و یعنی تست قرمز)؛ الگوی امن: `prev.remove_child(n)`
    بعد `next.add_child(n)` و بازیابی `global_position` **قبل** از جداکردن.
12. `assert_signal_emitted(obj, sig)` بدون `watch_signals(obj)` خودش fail می‌شود («is not being watched»).
13. `get_signal_parameters()` وقتی سیگنال emit نشده `null` می‌دهد؛ انتسابش به `Array` تایپ‌شده
    `SCRIPT ERROR` می‌سازد و پیام fail اصلی را می‌پوشاند → اول گارد `is Array`.
**دسته‌ی فاز ۳ (خروجی واقعی ۴ دور CI؛ سه‌تای اول دقیقاً «CI سبزِ توخالی» می‌ساختند):**
14. `project.godot` یک فایل INI/ConfigFile است و کامنتش **فقط `;`** است. سه خط `#` که بالای
    `LevelLoader=` گذاشتم باعث شد خودِ سطرِ autoload ثبت نشود → `Parse Error: Identifier
    "LevelLoader" not declared` در چهار فایل تست، درحالی‌که `--import`، `gdlint` و
    `validate_levels.py` همه سبز بودند. (بالای `run/main_scene` هم همین بود؛ یعنی ادعای
    «F5 صحنه را باز می‌کند» در فاز ۲ عملاً بی‌آزمون مانده بود.) نگهبان: `test_project_wiring.gd`.
15. `String % fmt` در Godot کاراکتر `%g` را **نمی‌شناسد**: `ERROR: String formatting error:
    unsupported format character` و GUT آن را به‌شکل `<engine-0>Method/function failed.`
    گزارش می‌کند که پیام اصلی تست را می‌پوشاند. از `%.3f` (یا `str()` و `+`) استفاده کن.
16. `String.split()` در 4.7 `PackedStringArray` برمی‌گرداند، نه `Array[String]`؛
    `var lines: Array[String] = text.split("\n")` = «Trying to assign a value of type
    `PackedStringArray`» و کل اسکریپت بارگذاری نمی‌شود.
17. `ProjectSettings.get_property_list()` آرایه‌ی `Dictionary` است (نه رشته)؛ برای پیمایش
    `autoload/*` باید `str(prop.get("name",""))` را بررسی کنی، وگرنه «Unable to iterate on
    value of type "Array[Dictionary]" with variable of type "String"».

### ADR-028 — قرارداد `config` سطح و قاعده‌ی برد (فاز ۲)
**زمینه:** سند ۰۴ فقط «Win detection در LevelController» را نام برده و شکل داده‌ی سطح در فاز ۳
(«LevelData از JSON §1») تعریف می‌شود. برای اینکه کد فاز ۲ در فاز ۳ **دوباره نوشته نشود**، قرارداد
`config` از همان الان قفل می‌شود و `default_config()` فاز ۲ دقیقاً همان شکل را تولید می‌کند:
```
{ level_id, tier, tolerance, narrative_intro,
  scales: [ { id,
              left_orbs: [{type,value}],  left_ghost_orbs: [{type,hidden_value}],
              right_orbs: [...],          right_ghost_orbs: [...] ,
              target_value } ],
  available_orbs: [ {type, value, count} ] }
```
**تصحیح در آغاز فاز ۳ (وقتی آرک‌تایپ ۲ «دو طرف نیمه‌پُر» اجرا شد): ** کلیدهای
`right_orbs`/`right_ghost_orbs` اضافه شدند — بدون آن‌ها سطح‌هایی که کفه‌ی راستشان از
قبل پر است ساخته نمی‌شدند (تست فاز ۳ همان را قرمز کرد). قاعده‌ی تازه: کره‌ی روح **فقط**
در کلید `*_ghost_orbs` می‌آید و در `*_orbs` تکرار نمی‌شود، وگرنه LevelController وزنش را
دو بار روی کفه می‌گذارد (تست `test_ghosts_live_only_in_the_ghost_keys`).
**تصمیم:**
- `type ∈ {number, ghost, negative}`؛ برای `ghost` کلید `hidden_value` و برای `negative` همان
  `value` (علامت را **نوع** تعیین می‌کند، نه داده → داده‌ی JSON هیچ‌وقت «-2» نمی‌شود).
- **برد**: `every scale: abs(left−right) <= tolerance` **و** حداقل یک کره چیده شده باشد.
  تطبیق با `target_value` عمداً استفاده نمی‌شود، چون `target_value = left + required` در سند داده‌ها
  آنگاه خودبه‌خود همیشه متعادل است. `target_value` فقط برای اعتبارسنجی/راهنما می‌ماند.
- **تلاش (attempt)**: فقط وقتی یک *جای‌گذاری* نتیجه‌اش نامتعادل باشد و وضعیت ≥ `0.8s` بماند
  (`attempt_settle_sec`)؛ بنابراین درگ‌های میانی و چیدمان اولیه‌ی سطح تلاش نیستند (قانون GDD §۳).
- `score` و `elo_delta` در این فاز placeholder‌اند (به ترتیب ۱.۰ و ۰.۰)؛ فاز ۴ آن‌ها را از
  `ErrorClassifier`/`DifficultyEngine` پر می‌کند. کلیدهای `stats` = اسکیمای §۵ سند داده‌ها
  (`time_to_solve_sec, hints_used, attempts, final_elo_delta`) + `score` داخلی.
**پیامد:** `LevelData.to_config_dict()` در فاز ۳ باید همین شکل را بدهد (تست برابری شکل اضافه می‌شود)؛
`tools/validate_levels.py` مرجع قابل‌حل‌بودن می‌ماند و `solution_spec` (ADR-006) منبع جواب است، نه
`target_value`.

### ADR-029 — `BalanceScale` ترکیبی‌پذیر است (پیش‌نمای Tier 4)
**زمینه:** Twin Observatory (Tier 4، GDD §۳) **دو** ترازوی پیوندخورده دارد؛ اگر ترازو تک‌نمونه و
وابسته به «سطح» طراحی شود، فاز ۴ یعنی بازنویسی هسته.
**تصمیم:** `LevelController` آرایه‌ای از `BalanceScale` می‌سازد و هیچ‌کدام از آن‌ها نمی‌داند «بردی در کار
است»؛ برد = «همه متعادل». سیگنال `EventBus.balance_changed(left,right)` (تسک ۱.۱) دست‌نخورده مانده و
`scale_state_changed(scale_id,left,right)` کنارش اضافه شد تا مصرف‌کننده‌های موجود (HUD/آنالیتیکس)
نشکنند و مصرف‌کننده‌ی چندترازویی شناسه داشته باشد. `_apply_scale_layout()` برای n>1 بازوها را کوتاه
(`arm_length=140`) و کفه‌ها را `pan_radius=96` می‌کند و ترازوها را در x جدا می‌کند — **مقیاس نود
تغییر نمی‌کند** تا هندسه‌ی `contains_point` در مختصات جهانی دقیق بماند (ADR-031).
**پیامد:** Tier 4 فقط داده است، نه کد. `LinkMechanic` (اینکه کره‌ی یک ترازو روی دیگری اثر بگذارد) در
فاز ۴ روی همین `scale_id`ها سوار می‌شود.

### ADR-032 — صحنه نقطه‌ی ترکیب است، درخت در کد ساخته می‌شود
**تصمیم:** `BalanceScale.tscn` فقط ریشه + اسکریپت است و `build_children()` (Pivot/Beam/LeftPan/RightPan)
را خود کد می‌سازد؛ `WeightOrb.tscn` برعکس، بچه‌هایش را دارد تا اسکریپت در هر دو حالت (صحنه و `new()`)
کار کند (`_ensure_nodes` کمبود را می‌سازد و شعاع shape را با `radius` همگام می‌کند).
**چرا:** صحنه‌های دستیِ nest‌شده با پراپرتی‌های تو در تو در فرمت تکستی، محتمل‌ترین منبع `Parse Error`
هستند (ADR-026 بند ۶) و رفتار ادیتور/هدلس را دوگانه می‌کنند. با این الگو صحنه در هر دو محیط **دقیقاً**
یک درخت می‌دهد و تست‌ها بدون ادیتور قابل‌تکرارند.

### ADR-033 — گارد کشف تست در CI (CI سبز ≠ تست‌ها اجرا شده‌اند)
**زمینه (اتفاق واقعی فاز ۲):** یک کامنت داخل `BalanceScale.tscn` باعث شد `BalanceScale.gd` کامپایل
نشود؛ GUT شش فایل تست را **بی‌صدا رد کرد** و با «Scripts 5 / 32 PASS» CI سبز شد. اگر شمارش نمی‌شد،
فاز ۲ با صفر تست مکانیک «سبز» merge می‌شد.
**تصمیم:** در `ci.yml` تعداد `test_*.gd` روی دیسک (بدون `support/`) با خط `Scripts` خلاصه‌ی GUT براب
کند؛ نابرابری = `::error` و قرمز. `tools/ci_annotate.py` هم بسته‌بندی شد (۱۲ annotation × ۸ خط، با
نام تستِ خط بالایی) چون سقف GitHub ۵۰ annotation برای هر check-run است و ۳۵ fail خط‌به‌خطا جا می‌ماند.
**پیامد:** هر اسکریپت تستِ «اجرا نشدن» (parse/compile) حالا قرمز است؛ نه فقط fail. این گارد در فازهای
۷ و ۹ (تولید انبوه تست/سطح) ارزشش دوچندان می‌شود.

### ADR-034 — نام فایل، منبع «وجود سطح» است؛ `level_id` داخل JSON باید با آن بخواند
**زمینه:** `LevelLoader.levels_for_tier()` سطح‌ها را از **فهرست دیسک** کشف می‌کند و id را از مسیر
می‌سازد (`data/levels/tier1/level_1_01.json` → `tier1_level_01`)، درحالی‌که `path_for()` مسیر را از
id می‌سازد. دو آینه‌ی هم‌بار. `tools/validate_levels.py` هم شماره‌ی آخر نام فایل را با `level_id`
مقایسه می‌کند. الگوی نام‌گذاری عمداً نامتقارن است: پوشه `tier<N>`، فایل `level_<N>_<NN>.json`.
**تصمیم:** قرارداد سه‌تایی **بسته** است و هر سه‌جا یک regex را دارند (`^tier([1-5])_level_([0-9]{2})$`
در `LevelLoader` و `LevelData`، `^tier[1-5]_level_\d{2}$` در ابزار پایتون): (۱) نام فایل، (۲) `level_id`
داخل فایل، (۳) `path_for()`. اگر یکی نخواند، ابزار پایتون خطا می‌دهد و تست فاز ۳ هم («همه‌ی idهای
کشف‌شده باید با `load_level` خوانده شوند و `validate()` خالی بدهند») همان را در CI می‌گیرد.
**چرا:** «سطح گم‌شده» در موتور باید یک *خطای گزارش‌شده* باشد (`level_load_failed`) نه صفحه‌ی سفید؛
این فقط وقتی ممکن است که تبدیل id↔مسیر یک تابع باشد، نه دو تابع مستقل که دستی هم‌گام نگه داشته می‌شوند.
**پیامد:** افزودن سطح = یک فایل JSON با نام درست + شماره‌ی پشت‌سرهم؛ هیچ ثبت‌نام دستی (manifest) لازم
نیست. در فاز ۷ (≈۵۰ سطح) همین ویژگی شرط لازمِ تولید انبوه است.

### ADR-035 — `pending_config` + `change_scene_on_start=false`؛ تست هرگز صحنه‌ی خودش را نمی‌کَنَد
**زمینه:** `LevelLoader.start_level()` باید صحنه را عوض کند، ولی در GUT اگر `change_scene_to_file()`
اجرا شود، درختِ همان تست (و خود نودِ در حال اجرا) آزاد می‌شود و بقیه‌ی تست‌ها بی‌معنی/معلق می‌شوند —
خطا هم به‌شکل timeout یا «object was freed» می‌آید و ریشه‌یابی‌اش سخت است.
**تصمیم:** جداسازی «ساختن config» از «رفتن به صحنه»: `start_level()` همیشه config را در
`pending_config` می‌گذارد و *اگر* `@export var change_scene_on_start` (پیش‌فرض `true`) روشن باشد
`change_scene_to_file(LEVEL_SCENE_PATH)` را صدا می‌کند. `LevelController._ready` با
`take_pending_config()` آن را برمی‌دارد و مصرف می‌کند (و `clear_pending_config()` در `before_each`
تمیزش می‌کند تا به تست بعدی نچمد). برای صحنه‌ی بعد از برد هم همین الگو: `LevelResultBar` سیگنال
`next_requested`/`map_requested` می‌دهد و تغییر صحنه تنها از `goto_map()`/`start_level()` انجام می‌شود؛
`WorldMap.allow_scene_change` هم برای همان کار است.
**چرا:** خواسته‌ی واقعی «صحنه عوض شود» را با خواسته‌ی «تست قابل‌تکرار باشد» نمی‌شود در یک تابع ادغام کرد؛
پرچمِ export ارزان‌ترین مرز است. در عوض جریان واقعی (F5 → نقشه → سطح → بعدی) در بازی روشن است و در تست
خاموش؛ و یک تست جدا (`test_project_wiring.gd`) ثابت می‌کند `main_scene` و صحنه‌ها load می‌شوند.
**پیامد:** هر سیستم تازه‌ای که صحنه عوض می‌کند (فاز ۶: منو، پاز، داشبورد والدین) باید همین شکل را بگیرد:
سیگنال + پرچم change_scene، نه `get_tree().change_scene_to_file()` مستقیم در منطق بازی.

### ADR-036 — داده‌ی JSON در پریست خروجی Android: `*.json` در Non-Resource Files (اقدام فاز ۱۰)
**زمینه:** سطوح از `res://data/levels/...` با `FileAccess` خوانده می‌شوند (نه به‌عنوان `.tres`). در
ویرایشگر و در `--headless` این فایل‌ها روی فایل‌سیستم واقعی‌اند و خوانده می‌شوند؛ در خروجی Android تنها
چیزی که داخل `PCK` می‌رود منابع import‌شده است، مگر الگوی «Non-Resource File Patterns» آن را بیاورد.
نتیجه‌ی غفلت: بازی روی دستگاه **بدون هیچ سطحی** بالا می‌آید و `level_load_failed` می‌دهد، درحالی‌که CI
و دسکتاپ کاملاً سبزند.
**تصمیم:** در `game/export_presets.cfg` برای پریست Android (و iOS/دسکتاپ در صورت نیاز) خط
`export/non_resource_files=PackedStringArray("*.json")` الزامی است؛ در `LevelLoader.LEVELS_ROOT` هم
همین یادآوری نوشته شده. فاز ۱۰ (تسک ۱۰.۳/۱۰.۴) باید روی دستگاه واقعی بررسی کند که
`DirAccess` همان پنج فایل را می‌بیند و `first_unfinished_id()` تهی نیست.
**چرا:** این تنها ریسک «فقط روی دستگاه» فاز ۳ است؛ نوشتنش به‌عنوان تصمیم، جلوی یادتان‌رفتن را در
فاز build می‌گیرد (به‌جای اینکه صرفاً یک کامنت در کد بماند).
**پیامد:** اگر بعداً بخواهیم داده را encrypt/compress کنیم، همین‌جا عوض می‌شود: یا `FileAccess.open_encrypted_with_pass`
یا تبدیل به `.tres` (که import می‌شود ولی ویرایش دستی JSON را از بین می‌برد — فعلاً JSON می‌ماند،
ADR-006).

### ADR-037 — `target_value` یعنی «وزنی که بازیکن باید به کفه‌ی راست **اضافه** کند»
**زمینه:** `03-DATA-SCHEMAS.md` §۱ آن را «وزن هدف روی کفه‌ی راست» نوشته؛ در سطوحی که
`right_side.fixed_orbs` دارند (آرک‌تایپ ۲، سطوح ۰۴ و ۰۵) این دو خوانش فرق می‌کند:
مجموعِ کفه = `left_total`، ولی مقدارِ لازم از سینی = `left_total − right_fixed`.
**تصمیم:** خوانش دوم معتبر است. `LevelData.validate()` می‌گوید
`abs((left_weight() − right_weight()) − target_value) ≤ 1e-6` (وقتی `tolerance=0` و بدون ghost)،
`tools/validate_levels.py` هم `left_total == target + right_fixed` را بررسی و DP را روی
`need = left_total − right_fixed` حل می‌کند. `required_right_weight()` همان «نیازِ بازیکن» را می‌دهد.
**چرا:** در موتور، برد از **تعادل دو کفه** می‌آید (`BalanceScale.is_balanced(tolerance)`)، پس
`target_value` یک عدد نویسندهگی/اعتبارسنجی است، نه ورودی قضاوت؛ معنای «اضافه‌ای که باید بسازی» برای
سطح‌سازی، DP و راهنماها (فاز ۵) مستقیم‌تر است. وقتی `fixed_orbs` راست خالی باشد (همه‌ی Tier 1 جز ۰۴/۰۵
و تمام نمونه‌های سند) دو خوانش یکی‌اند — پس این تصمیم با `03` در تضاد عملی نیست، فقط ابهامش را رفع می‌کند.
**پیامد:** تست `test_alternative_solutions_win_too` باید `pan.total_weight()` را با
`right_weight() + required_right_weight()` بسنجد، نه با نیاز تنها. اگر روزی خواستیم «هدف، مجموع کفه»
باشد، فقط همین ADR و دو خط validate/validator عوض می‌شوند.

### ADR-038 — `DifficultyEngine` نتیجه را با فراخوانی مستقیم می‌گیرد، نه با شنود `level_completed`
**زمینه:** سند ۰۴/سند ۰۷ §۵ می‌گویند «بعد از هر سطح، رتبه به‌روز شود». ساده‌ترین پیاده‌سازی
شنودِ `EventBus.level_completed` است، اما payload همان سیگنال باید `score` و `final_elo_delta`
را داشته باشد — یعنی رتبه **قبل از** emit باید محاسبه شده باشد. اگر موتور هم شنود کند، یک
نتیجه دو بار اعمال می‌شود (رتبه دو برابر بالا می‌رود) و اگر بعد از emit اعمال شود، payload صفر
می‌برد.
**تصمیم:** موتور هیچ سیگنالی از بازی نمی‌شنود. `LevelController._win()` صراحتاً
`DifficultyEngine.apply_level_result(config, true)` را صدا می‌زند، `score` و delta را از
خروجی‌اش می‌گیرد و همان‌ها را در `GameState.build_level_stats()` می‌گذارد. تنها ورودیِ
موتور از بیرون، `LevelLoader.next_selector` است (ADR-035) که خودش هم فراخوانی مستقیم است.
**چرا:** «چه اتفاقی افتاد» (EventBus، برای UI/آنالیتیکس) از «رتبه چه شد» (State، برای موتور)
جدا می‌ماند؛ ترتیبِ اعمال دیگر به ترتیب اتصالِ هندلرها وابسته نیست و تستِ رگرسیونِ ساده‌ای دارد:
`emit` کردنِ تنها نباید رتبه را تکان بدهد (`test_level_completed_signal_alone_does_not_move_the_rating`).
**پیامد:** هر مسیر بُردِ جدید (فاز ۶ «ستاره‌ی روز»؛ چالش‌های فاز ۹) باید صراحتاً
`apply_level_result` صدا بزند؛ اگر روزی EventBus به یک event-bus واقعی با replay تبدیل شد،
این ADR تنها راهِ اعمالِ رتبه باقی می‌ماند. وضعیتِ انباشته (`_no_hint_streak`، `_results`) روی
autoload زنده است و بعد از راه‌اندازی دوباره صفر می‌شود — عمداً ذخیره نمی‌شود، چون منبع
حقیقتِ رتبه‌ها `PlayerModel` است (ADR-015).

### ADR-039 — کلید مهارت = `concept_tags[0]`؛ برچسب‌ها با GDD §۴ هم‌نام می‌شوند
**زمینه:** `SkillRating` بر اساس «کلید مهارت» کار می‌کند و سند ۰۷ §۴ معیار خروج از Tier 1 را
`addition_basic ≥ 1050` نوشته، ولی پنج سطح Tier 1 در `concept_tags` برچسب‌های آزاد
(`addition`, `balance`, …) داشتند؛ یعنی آن معیار هیچ‌وقت خوانده نمی‌شد و رتبه‌ی هر مهارت
سراسری روی چند سطح پخش می‌شد.
**تصمیم:** کلید مهارت، **اولین** عنصر `concept_tags` است (`DifficultyEngine.tags_of`) و پنج فایل
Tier 1 به `["addition_basic", …]` تغییر کردند؛ `ALLOWED_CONCEPTS` در `tools/validate_levels.py`
هم همین کلیدها را می‌پذیرد. سایر tagها هم امتیاز می‌گیرند (یک برد روی همه‌ی برچسب‌های سطح) تا
مهارت‌های جانبی بی‌رکورد نمانند، ولی «رتبه‌ی فعلی بازیکن» برای انتخاب سطح = میانگین همان tagهاست.
**چرا:** یک سطح باید به یک مهارتِ «صاحب‌اختیار» وصل باشد وگرنه نردبانِ Tier و معیارهای خروج
در GDD معنی خود را از دست می‌دهند. نگه‌داشتنِ ترتیب آرایه به‌جای یک فیلد تازه (`primary_skill`)
هم انتخاب آگاهانه است: داده‌ی موجود نمی‌شکند و validator می‌تواند `concept_tags[0]` را الزامی کند.
**پیامد:** اگر روزی سطوحِ Tag-چندگانه رتبه را «می‌سوزانند» (یک بردِ `addition_basic` روی
`concrete_numbers` هم اثر می‌گذارد)، کافی است `tags_of` فقط عنصر اول را برگرداند — یک خط، بدون
تغییر داده. سند ۰۳ §۱ در `docs/` فقط *ساختار* را تعریف می‌کند؛ اسمِ valueها از GDD §۴ می‌آید
(و به همین دلیل `test_level_data.gd` هم به‌روزرسانی شد).

### ADR-040 — «سطح ساده‌تر» یعنی تمرینِ مجدّدِ یک سطحِ تمام‌شده، با قفلِ «یکی‌در‌میان»
**زمینه:** §۵ سند ۰۷: «۲ بار گیرکردن در یک سطح → سطح بعدی ساده‌تر، از همان Tier». اما validator
ممنوعیت پرشِ بیش از ۱۲۰ Elo درون یک Tier را اجبار می‌کند و نردبانِ هر Tier صعودی است؛ پس هیچ
کاندیدِ **بازِ** ساده‌تری وجود ندارد — «ساده‌تر» فقط می‌تواند بازگشت به یک سطحِ تمام‌شده باشد.
نخستین پیاده‌سازی (برداشتنِ ساده‌ترین کاندیدِ همان Tier) در شبیه‌سازی ۳۰ سطحی یک حلقه‌ی مرگ
ساخت: بازیکن ضعیف تا ابد بین دو سطح تاب می‌خورد و میانگین رتبه‌اش دقیقاً برابر بازیکن قوی شد
(farq = 0).
**تصمیم:** `struggle = GameState.level_attempts ≥ STRUGGLE_ATTEMPTS and not _remediation_used`؛
در حالت struggle، استخر کاندید با `include_completed = true` بازسازی می‌شود و
`_easiest_completed_in_tier()` ساده‌ترین سطحِ **تمام‌شدهٔ همان Tier** را برمی‌گرداند (reason
`struggle_practice_rerun`). `_remediation_used` در همان لحظه ست می‌شود و در `next_level` بعدی
بازنشانی می‌گردد؛ `reset_state()` هم پاکش می‌کند. اگر سطحِ تمام‌شده‌ای نباشد (بازیکن تازه)،
قاعده بی‌اثر است و همان پله‌ی نردبان می‌ماند.
**چرا:** «یکی‌در‌میان» دو خواسته را هم‌زمان تأمین می‌کند: بازیکن گیرکرده نفس می‌کشد و
مهارتِ شکست‌خورده را تمرین می‌کند، ولی در لوپِ بی‌پایانِ تمرین نمی‌افتد. قاعده را روی
«شکستِ کاملِ سطح» نگذاشتیم چون موتور از تلاش‌های همین سطح خبر دارد، نه از باخت.
**پیامد:** در شبیه‌سازیِ بازیکن ضعیف، ۱۴ از ۳۰ گام تمرینِ مجدّد است — شدتی که باید با
پلی‌تست واقعی (فاز ۱۱) قضاوت شود؛ اهرم‌های تنظیم: `STRUGGLE_ATTEMPTS` (۲) و اینکه آیا
`_remediation_used` باید بعد از یک برد پاک شود یا بعد از N برد. اگر آزاردهنده بود، ADR تازه
می‌نویسم — عددِ تست‌ها در `test_difficulty_simulation.gd` همان لحظه قفل می‌شود.


### ADR-041 — چرخشِ واریانت در `AriaController` است، نه در `HintTimingSystem`؛ `hint_shown` سه‌آرگومانه شد
**زمینه:** §۴ سند ۰۳ می‌گوید انتخاب واریانت «چرخشی نه تصادفی» است (هیچ واریانتی برای یک نشست
پشت‌سرهم تکرار نشود) ولی نمی‌گوید این cursor کجا زندگی کند. `HintTimingSystem` (فاز ۴) تصمیم‌گیرِ
زمانِ راهنماست و `hint_id` تولید می‌کند؛ انتخاب متن کار دیگری است.
**تصمیم:** cursor در `AriaController._cursor: Dictionary[hint_id → int]` است و انتخاب با
`text_for(cursor) = variants[absi(cursor) % n]` انجام می‌شود؛ `match_error()` فقط قالب را برمی‌گرداند
(توابع خالص، پس تست‌پذیر). سیگنال `EventBus.hint_shown` از `(hint_id, level_id)` به
`(hint_id, level_id, text)` ارتقا یافت تا هر UI (جعبه‌ی گفت‌وگو، لاگ والدین) همان متنی را ببیند که
کودک دیده است. `HintTimingSystem` هرگز متن نمی‌سازد.
**چرا:** اگر چرخش در سیستم زمان‌بندی باشد، هر مصرف‌کننده‌ی دیگر (مثلاً «دکمه‌ی راهنما» در HUD
فاز ۶ که `hint_requested` می‌فرستد) باید آن را دور بزند؛ با cursor در کنترلر، «هر منبعِ درخواست»
خودکار همان قانون را می‌گیرد. همچنین متن درونِ رویدادِ analytics می‌نشیند و ADR-010 (ثبت
ترن‌اسکریپت برای بازبینی انسانی) بدون UI جدید ممکن می‌شود.
**پیامد:** cursor بین دو نشست ذخیره نمی‌شود (رفتار جدید = از اول؛ برای کودک بی‌ضرر). تست
«تکرار نشدن پشت‌سرهم» روی `absi` نوشته شد، پس cursor منفی هم قانون را نمی‌شکند. اگر فاز ۸
«شخصیت‌های» Aria را چند لایه کرد، همان یک `hint_shown` کافی است.

### ADR-042 — متنِ خطا از `hint_id` دوم می‌آید و بعد از هر ۳ تلاشِ ناموفق تکرار می‌شود
**زمینه:** `error_detected(error_type)` فقط نوع خطا را می‌برد و §۴ سند ۰۳ می‌گوید پاسخ Aria باید
با `applies_to_error_types` همان خطا را پوشش دهد. سطوح فاز ۳ هم `hint_sequence` دارند (فقط پنج
`hint_id`: `gentle_nudge_01`، `compare_sides_01`، `inventory_count_01`، `sign_flip_01`،
`both_sides_01`) و هیچ‌کدام نوع خطای مشخص ندارند.
**تصمیم:** در `AriaController._on_error_detected`: اگر `fails` مضربی از `ERROR_HINT_EVERY_FAILS=3`
نباشد، فقط `aria_state_changed("thinking")` می‌رود (بی‌متن؛ کودک در حال تلاش است، نصیحت لازم
نیست). اگر مضرب بود، `hint_id` **دوم**ِ `hint_sequence` همان سطح (اگر بود، وگرنه `error_hint_id`
از همان نوع خطا) انتخاب می‌شود و `match_error` با `error_type` فیلتر می‌کند. `from_dict` هر قالبی
را که `applies_to_error_types` ناشناخته دارد رد می‌کند، و `validate_levels.py` هم `hint_id`های
سطح و هم پوشش «نوع خطا × Tier ۱-۲» را چک می‌کند (`MIN_HINT_TEMPLATES=15`).
**چرا:** دو قانون را هم‌زمان رعایت می‌کند: «هرگز جواب مستقیم نده» (متن‌ها صفر رقم‌اند) و «هر راهنما
قبلی تکراری نباشد»؛ با فیلتر `error_type`، متنِ خطایِ جهت هرگز برای خطای علامت نمایش داده نمی‌شود.
فیلد دوم `hint_sequence` عمداً انتخاب شد تا راهنمای خطا با راهنمای «پله‌ی اول» قاطی نشود.
**پیامد:** افزودن نوع خطای جدید در فاز ۷ یعنی: `ALLOWED_ERROR_TYPES` + یک قالبِ Tier ۱-۲ وگرنه
`validate_levels.py` CI را می‌شکند ✓ یعنی impossibleِ فراموشی.

### ADR-043 — هنر placeholder: هندسه در `_draw`، clipها در `_ready`، صحنه فقط «ریشه + اسکریپت»
**زمینه:** سند ۰۲ §۳ «آیاتا را چندوجهی نیمه‌شفاف با هسته‌ی رنگی بکش» و «فقط رنگ هسته state را عوض
کند» را می‌گوید؛ سند ۰۴ فاز ۵ «هنر موقت ولی منطق نهایی» را می‌خواهد و فاز ۸ هنر را جابه‌جا می‌کند.
اولین نسخه‌ی `Aria.tscn` گره‌های `Polygon2D` و `[sub_resource]`های رنگ داشت و تست‌ها باید
می‌گفتند آن‌ها چه‌اند.
**تصمیم:** `AriaCrystal`/`AriaCore` در `_draw()` می‌کشند (چندضلعی + خیره‌کنندگی روی `self_modulate`)
و هیچ فایلی به جز `.gd`/`.tscn` تولید نمی‌شود؛ هر شش clip در `_ready` با `AnimationLibrary`
ساخته می‌شوند و `build_placeholder_clips` (export) کلید فاز ۸ است؛ `play_state()` رنگ هسته را هم
مستقیم از `CORE_COLORS` ست می‌کند، پس تفکیک‌پذیری به salute بودن کیفریم‌ها وابسته نیست. صحنه‌ها
(`Aria.tscn`، `DialogueBox.tscn`) فقط ریشه + `script` دارند و بقیه‌ی گره‌ها در `_ready` ساخته
می‌شوند — **اصلاحِ این بند در فاز ۶:** مقصر `anchors_preset` نبود (کلیدِ نصفه‌نیمه‌ی
`layout_mode` **بدون** `anchors_preset` باعث می‌شد `instantiate()` نودِ Nil بدهد؛
`scenes/main/MainMenu.tscn` با `anchors_preset=1` بارها سالم بارگذاری و تست شده ✓ پس قاعده
درست این است: «صحنه‌های تازه یا کاملِ ویرایشی‌اند یا حداقلی: `load_steps` درست + ریشه با
anchors، و بقیه‌ی گره‌ها در `_ready`»).
**چرا:** SVG-first بودنِ ADR-007 و سقف حجم ریپو (≤ ۲۵MB) اجازه‌ی باینری/سبکِ دارایی نمی‌دهد، و
نگه‌داشتنِ هندسه در کد یعنی فاز ۸ فقط یک فایل `.tscn`/`.gd` را جابه‌جا می‌کند بدون دست‌زدن به
منطق یا تست‌ها ✓ «logic فریز» همان چیزی است که سند ۰۴ برای placeholder خواست.
**پیامد:** در فاز ۸ `build_placeholder_clips = false` و clipهای واقعی در `.tscn`؛ نام‌های state
ثابت‌اند چون `test_aria_avatar.gd` و `test_aria_controller.gd` فهرست را با هم مقایسه می‌کنند.
`set_state()` هم `state_changed` را emit می‌کند تا HUD (فاز ۶) برای «حلقه‌ی نور دور آواتار» به
 AnimationPlayer وابسته نباشد.

### ADR-044 — «کاملاً آفلاین» یک تست است، نه یک ادعا
**زمینه:** سند ۰۰ §۵ و فاز ۵ DoD: بازی باید offline-first بماند و هیچ درخواست خارجی نرود؛
`FeatureFlags.LIVE_AI_ENABLED` به‌تنهایی فقط مسیر فعال را می‌بندد، ولی یک `HTTPRequest` تصادفی در
یک فایل دیگر با flag خاموش هم داده می‌فرستد (و Play Families را می‌شکند).
**تصمیم:** `test_live_ai_provider.gd` همه‌ی `.gd`های `game/scripts` و `game/scenes` را می‌خواند و

**چرا:** تبدیل یک محدودیت حریم‌خصوصیتی به چیزی که CI نگهبانش است؛ کامنت‌ها حذف می‌شوند چون
«نوشتنِ اسم یک API در توضیح» نباید شکست بدهد، و همان کامنت‌ها دلیلِ قانون را توضیح می‌دهند.

باشد، **یا** این تست با ثبت یک ADR و بازبینی Play Families به‌روز شود — یعنی تغییر پروفایل
شبکه‌ی بازی بدون ریویو ممکن نیست. (بک‌اند فاز ۹ در `backend/` است و `game/scripts` را لمس نمی‌کند؛
`NetworkClient` طبق سند ۰۱ §۴ فقط در `game/modules/sync/` خواهد نشست ⇒ آنجا این تست فعلاً نگاه
نمی‌کند، و در فاز ۹ باید مرزِ مجازِ شبکه صریحاً ثبت شود.)


> یادداشت اجرایی (۱۴۰۵-۰۶-۱۸): ADR-044 یک بند «فاز ۹» دارد که باز است — وقتی `modules/sync/`
> ساخته شد، باید فهرست مجازِ شبکه‌ی بازی صریحاً مشخص شود (پوششِ تست یا استثنا). این تنها ADR بازِ
> مربوط به فاز ۵ است.

### ADR-045 — تنظیمات دستگاه در فایلِ **جدا** از `PlayerModel` (با SPECِ یکپارچه)
**زمینه:** سند ۰۱ §۴ فقط `PlayerModel` را تعریف کرده، ولی تنظیمات (زبان، دو ولوم، لرزش،
سویچ تطبیق، آواتار، پرچمِ اتمامِ آموزش) ویژگیِ **دستگاه/نشست**‌اند و مدل ویژگیِ **کودک** است؛
همه‌چیز در یک فایل یعنی هر بار که مدل sync شود (فاز ۹) ترجیحِ یک دستگاه به دستگاه دیگر سوار
می‌شود و خروجیِ «بازبینی والد» پر از کلیدِ غیرضروری می‌شود (سطحِ حریم‌خصوصیِ Play Families ✗).
**تصمیم:** `scripts/ui/SettingsStore.gd` به‌عنوان autoload: جدول `SPEC` (کلید ← نوع + بازه +
clamp)، `load_from(path)/save_to(path)/reset/restore_defaults/reset_for_tests`،
`get_value/set_value` (فقط حافظه ⇒ قابل‌تست) و `set_and_save/toggle` (ثبت روی دیسک)،
و چهار apply مجزا: `apply_at_boot` (فایل را می‌خواند و همه‌چیز را می‌چسباند)،
`apply_audio` (باس‌ها روی `AudioServer`)، `apply_locale` (`Loc.set_locale` +
`TranslationServer`، RTL در همین است)، `apply_gameplay_flags` (`DifficultyEngine.adaptive_selection`).
آواتار هم همین‌جاست (`avatar()/set_avatar_choice`) چون «ظاهر» تنظیم است نه پیشرفت.
**چرا:** یک جدولِ clamp یعنی «هر چه از دیسک آمد باور نمی‌شود» ⇒ تست
`test_out_of_range_and_wrong_types_are_clamped_not_trusted` ولوم ۹.0 را ۱.0 و `locale: "de"` را
`fa` می‌بیند؛ و جدابودن فایل یعنی تست‌ها می‌توانند مسیر را به `user://test_*.json` ببرند بدون
دست‌زدن به دادهٔ بازی ✓ (که `PlayerModel` هم از آن استفاده می‌کند).
**پیامد:** دو فایل روی دیسک؛ `restore_defaults()` **نباید** `apply_at_boot()` را صدا بزند
(چون فایلِ مسیرِ واقعی را دوباره می‌خواند و در تستِ با مسیرِ عوض‌شده، دیسک و حافظه واگرا
می‌شوند) ⇒ مستقیماً `apply_locale/apply_audio/apply_gameplay_flags` را صدا می‌زند و هیچ
پیشرفتِ کودکی را پاک نمی‌کند. `export_json_for_parent()` هم عمداً کلید `settings` ندارد
(`test_parent_dashboard.gd` همین را assert می‌کند).
### ADR-046 — حسابداری «زمانِ پاز» در `GameState` است؛ تنظیمات روی پاز **سوار** می‌شود
**زمینه:** §۶.۳ «resume کامل» و §۶.۵ «زمان بازی دقیق». اگر پاز شمرده شود، هم
`avg_time_to_solve_sec` (مبنای سختی تطبیقی) و هم `total_playtime_sec` (چیزی که والد می‌بیند) و هم
ساعت escalation راهنما دروغ می‌گویند؛ و کودک تشنه‌ای که ۹۰ ثانیه پاز می‌کند «سطح سخت» می‌شود ✗.
**تصمیم:** سه شمارنده در `GameState` (`_level_paused_msec`, `_session_paused_msec`,
`_session_paused_billed_msec`) + `_pause_open_msec`، با `begin_pause()/end_pause()/is_pause_open()`
و `reset_time_windows_for_tests()`. `elapsed_level_sec()` و `session_playtime_sec()` پاز را کم
می‌کنند و `commit_playtime()` **فقط تفاضلِ «پازِ کسرشده تا آخرین commit»** را از پنجره کم می‌کند.
`PauseMenu` هیچ منطقی ندارد جز UI: `open()` درخت را فریز + `controller.set_drag_enabled(false)`،
و «تنظیمات» به‌جای `change_scene` یک اورلی روی همان صحنه است.
**چرا:** اورلی = «resume از همان‌جا» بدون هیچ reload و بدون هیچ حالتِ نیمه‌باز ✗✓ و منطقِ پاز یک‌جا
است (پاز، قفلِ والدین و بعداً کات‌سینِ سه‌خطیِ فاز ۸ هم همین سه تابع را صدا می‌زنند).
**پیامد (با یک باگِ واقعیِ همین فاز):** نگه‌داشتنِ «مجموع pauseهای بسته‌شده» کافی نبود — pauseِ
**باز** در دو commit پشت‌سرهم دوبار کسر می‌شد و زمانِ واقعیِ بازی صفر می‌شد ✗ تستِ «دو پنجره را
مقایسه کن، هرگز زمان مطلق نسنج» همان روز گرفت ✓. `_session_paused_billed_msec` دقیقاً برای این
اضافه شد، و تست باید `begin_level()` را صدا کند (وگرنه `elapsed_level_sec()` از
`session_started_msec` بی‌کران بزرگ می‌شود).
### ADR-047 — قفلِ والدین «اصطکاک» است، نه امنیت
**زمینه:** §۶.۵: «یک قفل سادهٔ سؤال ریاضی بزرگسال … تا کودک به‌طور تصادفی وارد نشود». یک قفلِ
واقعی (PIN/حساب) بازیابی می‌خواهد؛ بازیابی یعنی ایمیل/تلفن ⇒ نقض §۵ سند ۰۰ و سیاست Families ✗✗
و یعنی والدِ قفل‌شدهٔ ناامید، اپ را حذف می‌کند.
**تصمیم:** `ParentGate` = یک عبارت `دُرقمی × دُرقمی`، ورودی با `LineEdit` و **قالب‌گشای ارقام
فارسی/عربی** (صفحه‌کلید فارسی Android رقم لاتین تولید نمی‌کند ✗ «۱۲a» رد می‌شود نه تصحیح خودکار،
چون کودک باید بداند چه زده)، سه حقِ تلاش، سپس قفلِ نشست تا خروج. پاسخ هیچ‌جا نوشته نمی‌شود:
نه برچسب، نه `describe()»، و «سؤال دیگر» بعد از قفل فرصت تازه نمی‌دهد. `make_question(seed)`
قطعی است تا شکستِ تست در CI بازتولیدپذیر باشد.
**چرا:** با یک ادعای صادقانه، «امنیت» به OS واگذار می‌شود (Kids Space/Family Link خودشان
رمزِ عبور دارند) و ما چیزی نمی‌فروشیم که نداریم ✓ تستِ «پاسخ روی هیچ Label/Button صفحه نیست»
همین ادعا را mechanic می‌کند.
**پیامد:** قفل **داخل** `scenes/ui/ParentDashboard.tscn` ساخته می‌شود، پس هر مسیری که این صحنه را
باز کند از آن می‌گذرد (و `MainMenu` فقط مسیر می‌فرستد)؛ `reveal_without_gate_for_debug` فقط
دیباگ است و پیش‌فرضش در بازی false است (تست assert می‌کند). اگر_owner_ بعداً PIN خواست، جای
گسترش همین فایل است + یک ADR تازه، نه «رمز در PlayerModel».
### ADR-048 — لاگِ آریا «چه گفت» را هم نگه می‌دارد؛ ثبت در **تولیدکننده**، نه در UI
**زمینه:** §۲ سند داده‌ها `aria_transcript_log` را «مبنای شفافیت برای والد» تعریف کرده بود با سه
فیلد (timestamp/hint_id/level_id) ⇒ داشبورد فقط کلیدِ قالب را نشان می‌داد، نه جمله‌ای که کودک
دیده ✗ ضمناً `PlayerModel.record_hint_shown()` از فاز ۱ هیچ فراخوانی نداشت (لاگ همیشه تهی).
**تصمیم:** فیلد چهارمِ **اختیاری** `text` (پیش‌فرض تهی ⇒ سیوهای قدیمی بدون خطا بارگذاری می‌شوند)
و فراخوانی در `AriaController.show_hint()` — تنها جایی که یک متنِ کودک‌دیده تولید می‌شود.
**چرا:** ثبت در UI یعنی هر مسیرِ تازه (برنامه‌ای، کات‌سین، فاز ۸) می‌تواند لاگ را رد کند ✗؛ ثبت در
تولیدکننده یعنی «اگر دیده شد، ثبت هم شد» ✓ و `hint_usage_rate` دیگر با «چه گفت» قابل‌تطبیق است.
**پیامد:** `ParentDashboard` ردیف‌ها را کامل می‌سازد (تست با ۱۲۰ ورودی: هیچ `slice[-N]` ندارد ✓
«قابل‌اسکرول» با `ScrollContainer`)؛ سقفِ `PlayerModel.MAX_TRANSCRIPT_ENTRIES = 500` (فاز ۱) تنها
حذف‌کننده است — در MVP (≈۶۰ سطح × ≈۴ راهنما = ۲۴۰) هرگز پر نمی‌شود ✓ اگر فاز ۷ محتوای بیشتری
آورد، یا سقف بالا می‌رود یا آرشیو به `POST /api/events` می‌رود (خانهٔ درستش؛ ADR-044) و این یک
**محدودیتِ ثبت‌شده** است، نه سکوت.
### ADR-049 — کفِ لمسی ۱۴۴px در **کد**، با ممیزی خودکار روی هر صحنه
**زمینه:** §۷ سند ۰۲ «حداقل ۴۸dp» و §۳ سند ۰۰ «دستگاه ارزان هم هدف است»؛ این دو روی کاغذ بودند
و دو صحنهٔ فاز ۳ (`WorldMap.NODE_SIZE = 136`, `LevelResultBar.BUTTON_SIZE.y = 112`) نقضش می‌کردند.
**تصمیم:** `UIKit.MIN_TOUCH_PX = MIN_TOUCH_DP * CANVAS_PX_PER_DP = ۴۸ × ۳ = ۱۴۴` (بومِ بازی ۱۰۸۰×۱۹۲۰ است و `px_for_dp()` تنها نقطهٔ تبدیل؛ ضریب ۳ یعنی mdpiِ ارزان‌ترین هدف)؛
`style_button/make_button` کف را در `custom_minimum_size` می‌گذارند؛
`UIKit.audit_touch_targets(root)` روی فهرست **صریحِ** کلاس‌های قابل‌کلیک (`CLICKABLE`) می‌گردد و
متخلف را با `max(size, custom_minimum_size)` روی هر محور قضاوت می‌کند و **نام خود گره** را
گزارش می‌دهد. هر تستِ UI تازه، در انتها `assert_true(audit.is_empty())` می‌زند.
**چرا:** قانونی که ابزار نگهبانش نباشد، آرام آرام نقض می‌شود ✓ (این‌جا خودش دو نقض موجود را گرفت)؛
و `max(...)` ضروری است چون در هدلس layout اجرا نمی‌شود و `size` صفر است — بی‌این، هر دکمهٔ درست هم
قرمز می‌شد ✗ نسخهٔ اولِ خودِ ممیز دو باگ داشت (مسیرِ ریشه به‌جای نامِ متخلف، و min_size به‌جای
max) که تستِ خودش گرفت ✓✓ ابزارِ تست‌شده = ابزارِ قابل‌اتکا.
**پیامد:** ضریبِ ۳ یک **فرض** است؛ فاز ۱۰ روی دستگاه واقعیِ ارزان اندازه می‌گیرد و اگر چگالی‌اش
متفاوت بود تنها همین ثابت عوض می‌شود (`px_for_dp` تنها نقطهٔ تبدیل است). دکمه‌های

### ADR-050 — گامِ دومِ آموزش همان `LevelController`ِ واقعی است، با bookkeeping خاموش
**زمینه:** §۶.۲ «آموزش در بستر بازی، فقط عمل» ✗ کپی‌کردن منطق ترازو در یک «صحنهٔ آموزشی» یعنی
دو پیاده‌سازی که در فاز ۷ از هم واگرا می‌شوند؛ و اجازه دادن به آموزش برای نوشتنِ آمار،
مبنای سختیِ تطبیقی را از همان ابتدا آلوده می‌کند ✗ (کودک در آموزش عمداً اشتباه می‌کند تا یاد بگیرد!).
**تصمیم:** `Onboarding` (گام ۲) یک `LevelController` واقعی می‌سازد با configِ **در حافظه**

**چرا:** مکانیکِ تمرینی = مکانیکِ بازی ⇒ تست‌های فاز ۳/۴ همان را می‌سنجند؛ خاموش‌کردنِ
`report_progress` تنها راهِ درست بود (نه حذفِ `mark_level_completed` از مسیر ⇒ همان کد اجرا
می‌شود و فقط «ثبت» نمی‌کند ✓ پس اگر روزی ثبت پیشرفت خراب شود، آموزش هم می‌گیردش).
**پیامد:** در تست‌ها: `levels_completed`/`level_attempts`/`error_patterns`/`aria_transcript_log`
همه بعد از بردِ آموزش تهی می‌مانند (assert شده ✓✓ DoD ۶.۲)؛ دو قاعده‌ی فنی که با خون نوشته شد:
holder فیزیکِ آموزش **نباید** فرزند VBox باشد (layout، transformِ فیزیک را بهم می‌ریزد) و
`drag_enabled` باید با `visible` گام همگام شود (وگرنه کره‌ها از پشتِ صفحهٔ آواتار کشیده می‌شوند ✗)؛
`attempt_settle_sec` در تست کم می‌شود، زمانِ مطلق هرگز سنجیده نمی‌شود.
### ADR-051 — رشته در `meta["loc_key"]`، داده در `make_raw_label`؛ و پیاده‌روی UI بر پایهٔ کلاس
**زمینه:** §۶.۳ «تعویض زبان بی‌اجرای‌مجدد». راهِ ساده («همه‌جا `Loc.t` صدا بزن») دو مشکل دارد: هر

پاک می‌شوند ✗✗ (همین اتفاق در فاز ۶ افتاد: «۳ ساعت» جای خودش را به «زمان بازی» داد).
**تصمیم:** `make_label/make_button` کلید را در `meta["loc_key"]` می‌نویسند؛ `UIKit.retranslate(root)`

یعنی state‌های داینامیک هم از همان مکانیزم تغذیه می‌شوند (و بی‌هیچ if/else مترجم‌محور).
**پیامد:** برای فازهای ۷..۱۲: هر صحنهٔ تازه‌ای که `apply_flow/retranslate` می‌گیرد باید لیست
کلاس‌هایش **صریح** باشد (هرگز `is Control`)؛ هر عددِ مدل که در UI نوشته می‌شود `make_raw_label`؛

### ADR-052 — نقشهٔ سطح صفحه‌بندی‌شده است (صفحاتِ داخلِ Tier)، نه اسکرول و نه نودِ ریز
**زمینه:** `WorldMap` همهٔ سطوح را در یک باندِ ثابت (`TOP_Y..BOTTOM_Y` = ۱۲۶۰px) با
`step = band/(n-1)` می‌چید. با ۵ سطحِ فاز ۳ سالم بود؛ Tier ۲ (۱۵ سطح) گام را به ۹۰px رساند و
نودِ ۱۴۴px روی نودِ قبلی افتاد ✗✗ تستِ «برخوردِ مستطیل‌ها» در `test_world_map.gd` همان را در CI
گرفت؛ با ≈۴۵ سطحِ MVP، گام ۲۸px می‌شد ⇒ نقشه عملاً غیرقابل‌استفاده ✓ (هیچ بازبینیِ انسانی با ۵
سطح این را نمی‌دید).
**تصمیم:** صفحه‌بندی. `page_max()` = ‎`int(band / (NODE_HEIGHT + 60)) + 1`‎ ⇒ سقفِ نود از **باندِ
واقعی** حساب می‌شود، نه از عددِ دست‌نویس؛ صفحات **هیچ‌وقت وسطِ یک Tier نمی‌شکنند** (هر Tier
خودش صفحه‌بندی می‌شود و اگر ۹ سطح داشت، به ۵+۴ تقسیم می‌شود نه ۸+۱)؛ صفحهٔ پیش‌فرض، صفحهٔ
«اولین سطحِ بازِ تمام‌نشده» است؛ ناوبری با دو دکمهٔ `common.previous/next` به‌اندازهٔ کفِ لمسی و
یک شمارندهٔ رقمی (`Loc.digits`) انجام می‌شود و وقتی یک صفحه است، پنهان می‌ماند (⇒ نقشهٔ فاز ۳
تغییرِ ظاهری نمی‌کند ✓). API عمومی `goto_page(i)` است تا تست و ناوبریِ بعدیِ بازی به نام‌های
زیرخطی دست نزنند.
**چرا:** گزینهٔ «نود را ریز کن» کفِ دست‌رسپذیری §۷ سند هنری (۱۴۴px ≈ ۴۸dp) را می‌شکند ✗؛ گزینهٔ
`ScrollContainer` هم ریشه را از `Node2D` به `Control` می‌برد و هم کشیدنِ لمسی روی `Button` (که
`MOUSE_FILTER_STOP` دارد) اسکرول نمی‌کند ⇒ کودک ۹ ساله گیر می‌کند ✗؛ صفحه‌بندی هر دو خطر را ندارد
و «یک جهان کامل در یک نگاه» را که GDD §۵ می‌خواهد، حفظ می‌کند. سه درسِ فنیِ همين تغییر: (۱) `const`
در GDScript فقط عملگر می‌پذیرد — `int((B - T) / P)` و `NODE_SIZE.y` در جایگاه ثابت خطای parse‌اند ⇒
تابع؛ (۲) `bind(state)` در لحظهٔ `connect` منجمد می‌شود ⇒ دکمهٔ «قبلی» از صفحهٔ دوم همیشه صفر
می‌داد، پس دلتا در تابع خوانده می‌شود؛ (۳) نتیجهٔ `get_node()` را باید با `as` تایپ کرد، چون
`Node` عضوِ `visible/.disabled` ندارد و هدلس ویرایشگری برای بخشودن ندارد.
**پیامد:** برای ۷.۲..۷.۴ و فاز ۱۰: هر Tierِ تازه **باید** با `test_world_map.gd` (برخورد/ابعاد/
بیرون‌زدگی، به‌ازای هر صفحه) و ممیزیِ `UIKit` سنجیده شود، نه فقط با `validate_levels.py` —
رشدِ محتوا UI را هم می‌شکند ✓✓ و عددِ شمارشِ محتوا هیچ‌جا در تست‌ها دست‌نویس نمی‌ماند
(سه تستِ فاز ۳/۴ که «هنوز Tier 2 ننوشته شده» را فرض می‌کردند، رفتارِ درست را «باگ» گزارش
می‌کردند ⇒ همه به استنتاج از دیسک/موتور تبدیل شدند؛ این قاعدهٔ عمومیِ پروژه شد).

### ADR-053 — «حرکتِ اشتباه» باید در **هر ترتیبی** ببازد: هیچ زیرمجموعه‌ای تراز نکند
**زمینه:** هر سطح `solution_spec.wrong_ops.right_orbs` را به‌عنوان «اشتباهِ آموزشیِ رایج»
می‌نویسد و باتِ فاز ۷ باید نشان دهد همان حرکت **نمی‌بَرد** ✓ در اولین اجرای CI، دو سطح از
Tier ۲ قرمز شدند ✗✓ چون `wrong_ops` آن‌ها «حلِ درست + یک کرهٔ اضافه» بود (۲_۰۱: `[5,5,2,-2]`
درحالی‌که `[5,5,2]` برنده است): یعنی حرکتِ اشتباه در عمل یک بردِ دیگر بود، و اگر کره‌های
برنده جلوتر چیده شوند، کودک **بَرد** ✓✗ قاعدهٔ قبلیِ من فقط «مجموعِ لیست ≠ نیاز» را می‌سنجید ✗
که این حالت را سبز رها می‌کرد.
**تصمیم:** دو لایه، یک ادعا.
• `tools/validate_levels.py`: روی `wrong_ops.right_orbs` **توان قدری زیرمجموعه** (با ترتیبِ
  چندگانگی) بررسی می‌شود و اگر هیچ زیرمجموعه‌ای تا `tolerance`ِ سطح با نیاز کفه نخواند، خطاست
  ⇒ «اشتباه» یعنی *هیچ* subsetِ آن تراز نکند (نه اینکه مجموعِ کل تراز نباشد ✗)؛
• `test_all_content_playable.gd`: کره‌ها **یکی‌یکی** سرِ کفه می‌نشینند و بعد از هر کره
  `is_won()` باید false باشد ⇒ اگر موتور برد را latch کند یا ترتیبِ داده برد را زودتر فعال
  کند، همین‌جا می‌افتد ✓ (validator ترتیب‌ها را می‌بندد و تستِ GUTِ رفتارِ موتور را ✓✓ هر دو
  لازم‌اند: یکی داده، دیگری موتور).
ضمناً داده اصلاح شد: ۲_۰۱ ⇒ `[5,5]` («کرهٔ کوچک جا ماند») و ۲_۰۷ ⇒ `[9,9]` («فقط دو تا
درشت را برداشتی، به عددِ هدف نگاه نکردی») — هر دو **نزدیکِ غلط**✗✓ نه غلطِ بی‌ربط، چون
ارزشِ آموزشیِ Tier ۲ همین است که کودک *تفاوتِ یک کره* را حس کند §۴ سند ۰۴ ✓
**چرا:** سطحی که «اشتباه» در آن ببرد، مفهوم را نمی‌آموزد و `ErrorClassifier` هم هیچ
`error_type` برای آن تولید نمی‌کند ⇒ دادهٔ آموزشی و آمارِ والدین هر دو بی‌معنا می‌شوند ✗✓
(و این را هیچ تستِ دستی‌ای در ۴۵ سطح پیدا نمی‌کند).
**پیامد:** برای ۷.۲..۷.۴ هر `wrong_ops` باید subset-check را رد کند؛ چون توانِ زیرمجموعه روی
لیست‌های ≤ ۴ عنصر است، هزینه‌اش در CI ناچیز می‌ماند — اگر روزی لیست‌ها بلندتر شدند، به‌جای
DPِ کامل از همان `reachable_sums` استفاده می‌کنیم (عددِ آستانه را اینجا ثابت نمی‌گذاریم ✗✓).
و قاعدهٔ کلیِ فاز ۷: «هر ادعای داده‌ای که فقط *یک* ترتیبش سنجیده می‌شود، ادعای نصفه‌است» ✓

### ADR-054 — Tier ۳ = شبح + کسر: مجهول هرگز در سینی نمی‌آید و وزن‌ها مضربِ ۰٫۲۵‌اند
**زمینه:** معیار خروجِ Tier ۳ در docs/07 §۴ «استنتاجِ عدد ناشناخته» (`unknown_variable`,
`ghost_algebra`) و کار با کسر است ✓ `GhostOrb` از فاز ۲ در موتور بود ولی **هیچ سطحی** تا
امروز از آن استفاده نکرده بود ✗✓ یعنی برای اولین بار، «وزنِ مخفی» باید در سه لایه یکی
بماند: `WeightOrb.weight()` در موتور، `orb_weight()` در `validate_levels.py`، و `target_value`

• شبح **فقط** در `left_side.ghost_orbs` / `right_side.ghost_orbs` می‌نشیند و هرگز در
  `available_orbs` ✗✓ («مجهول» اگر قابل‌چینش باشد، دیگر مجهول نیست — قاعدهٔ ADR-028 و در
  validator سخت‌گیری شده ✓)؛ `hidden_value` هم به `leak_numbers` می‌رود ⇒ هیچ راهنمایی عددش

• **قاعدهٔ دادهٔ تازه:** هر وزنِ غیرصحیح باید مضربِ `0.25` باشد ✓✓ دلیلش فنی است، نه سلیقه‌ای:

  می‌زند؛ مضاربِ ۰٫۲۵/۰٫۵ در باینری دقیق‌اند ⇒ «تراز یا نبودن» در دو پیاده‌سازی عیناً یکی است،
  و عددی مثل ۰٫۱ می‌توانست در یک لایه تراز و در لایهٔ دیگر «یک‌سنتِ تلورانس» نباشد ✗✗
  (سطح‌های Tier ۳: ۳٫۵، ۴٫۵، ۶٫۵، ۱۲٫۵ … همه ×۰٫۲۵ ✓). اگر روزی کسرِ غیرِ ۴/۱ لازم شد،
  راهش آوردنِ همان `tolerance` به موتور است، نه رُند کردنِ عدد در داده ✗.
• `tolerance: 0.25` فقط یک سطح (۳_۰۵) ✓✓ «نزدیک کافی نیست» باید استثنای دیدنی باشد، نه حالتِ
  پیش‌فرض ✗✓ (و همان‌جا `wrong_ops = [5,1]` عمداً ۰٫۵ اختلاف دارد ⇒ بیرونِ کران ✓ تستِ
  «هیچ زیرمجموعه‌ای تراز نکند» (ADR-053) دقیقاً روی همین کران سنجیده می‌شود ✓).
• در سطح‌های شبح‌دار، `wrong_ops` = **همان اشتباهِ مفهومی** است، نه اشتباهِ حسابی: ۳_۰۶

• وجهِ تازهٔ همین دور: گیتِ بهداشتِ متن، **توضیحِ باگِ خودم** را هم قرمز کرد (سه کاراکتر چینی که ناخواسته در

`_sender.last_body()` پیش از هر `flush_once()` ⇒ `sent` خالی ⇒ «۰ ≠ ۶» ✓؛ رفعش سه assertِ *بیشتر* آورد:
`flush_once()==6` · `sent.size()==1` «یک دسته نه شش درخواست» ✓§۹.۴ · `queue_size()==0` ✓) و دیگری

### ADR-065 — آنالیتیکس: ناظرِ EventBus · کمینه (نه آینه) · با sinkِ تزریق‌پذیرِ هم‌نوع

**زمینه:** DoD ۱۰.۳ یک جمله دارد ✓✗ «یک جلسۀ کامل بازی، تمام رویدادهای مورد انتظار را در جدول
`events` بک‌اند ثبت می‌کند» — و سه فشار هم‌زمان روی آن است: (۱) §۵ فقط **شش** نوع رویداد را می‌شناسد
و `EventSchema` بک‌اند `.strict()` است ⇒ یک کلیدِ اضافی یعنی ۴۰۰ برای **کلِ دسته**، نه فقط آن سطر ✗✓
(۲) §۹/سیاست Families: هر بایتِ اضافه‌ای که از دستگاه کودک بیرون می‌رود باید دلیل داشته باشد ✗
(۳) این کلاس باید در هدلسِ GUT آزموده شود، درحالی‌که مصرف‌کنندۀ واقعی‌اش (`NetworkClient`) autoload است
و نوشتن در آن، وضعیتِ تست‌های دیگر را آلوده می‌کند ✗✓.

**تصمیم:**
• **ناظر، نه تولیدکننده** ✓ — هر شش سیگنال از قبل در نقاطِ درستِ کد emit می‌شوند
  (`GameState:58/75/229`، `LevelController:591/619`، `AriaController:128`)؛ `AnalyticsManager` فقط
  ترجمه می‌کند ✓ ⇒ DoD ۱۰.۳ بدونِ یک خط تغییرِ رفتار در گیم‌پلی بسته شد ✓ (blast radius = صفر ✓).
• **`const HANDLERS` = قراردادِ قابل‌سنجش** ✓✗ به‌جای listِ دومِ نام‌ها، «نقشۀ رویداد→هندلر» تنها
  جایِ اعلامِ انواع در این فایل است و **سه** سمت به آن قفل شده‌اند: تستِ GUTِ ۱ (هر نوعِ
  `NetworkClient.EVENT_TYPES` هندلر دارد ✓)، تستِ ۱/۲ (اندازه=۶ و هیچ نوعِ خارجِ enum ✓) و
  `check_backend_client_contract()` بندِ ۴ که فایل را می‌خواند ✓ ⇒ افزودن enum در سرور بدونِ trigger
  در بازی = CI قرمز ✓✓ (پروب: حذفِ `error_occurred` ⇒ قرمزِ درست ✓).
• **کمینه، نه آینه** ✓§۹ — `hint_shown` فقط `hint_id` را می‌برد و **متنِ راهنما هرگز بیرون نمی‌رود** ✗✓
  (پارامتر سومِ هندلر `_text` نام گرفته تا فراموش نشود که عمداً مصرف نمی‌شود ✓✓؛ تستِ ۵ با
  `JSON.stringify` اثبات می‌کند آن رشته هیچ‌جای رویداد نیست ✓). `score` هم که در مدلِ دستگاه هست
  نمی‌رود (چهار کلیدِ §۵ کافی است ✓)، و `timestamp` **اینجا** ساخته نمی‌شود — منبعش
  `NetworkClient._now_iso()` است ✓ (دو منبعِ زمان = دو قالبِ ممکن = ۴۲۲ تصادفی ✗✓ درسِ ۹.۶).
• **payload تخت، با شمارش** ✓ — `flatten_payload` فقط `JsonScalar`ِ بک‌اند را نگه می‌دارد
  (عدد/بول/نال/رشتهٔ ≤ 200 ✓ همان مرزِ `z.string().max(200)` ✓) و هر چیزِ تودرتو **می‌افتد ولی
  شمرده می‌شود** (`stats().dropped_payload_keys`) ✓؛ رشتهٔ ۲۰۱ کاراکتری «بریده» نمی‌شود ✗ (نصفه‌معنا
  از دادهٔ بدتر است ✓).
• **خاموش ⇒ ساخته نمی‌شود** ✓ — اگر `cloud_sync_enabled` والد خاموش باشد، `enabled()` در همان
  ابتدای `_send` برمی‌گرداند: نه رویداد، نه صف، نه حافظه ✓ (تستِ ۱۴)؛ «بساز و دور بریز» هم کار می‌کرد
  ولی صفِ فقط-حافظه را بی‌دلیل پُر و `dropped` را معنادار-بی‌معنا می‌کرد ✗✓.
• **`session_end` یک‌بار در هر نشست** ✓✗ دو مسیر به آن می‌رسند: `Window.focus_exited` (اندروید: اپ به
  بک‌گراند ⇒ تنها فرصتِ واقعیِ flush ✗✓ چون `NOTIFICATION_PREDELETE` دیر است) و `GameState` در
  PREDELETE ✓؛ `_session_end_sent` دومی را می‌بندد و `session_start` دوباره بازش می‌کند (سوئیچِ پروفایل ✓
  تستِ ۱۱/۱۲). اتصالِ `focus_exited` عمداً با `has_signal` + `connect("focus_exited", …)` (رشته ✓)
  نوشته شد: اگر در نسخه‌ای چنین سیگنالی نبود، **فایل parse نمی‌شد و ۲۰ تست می‌مرد** ✗✓ — این‌جا
  بدترین حالت فقط خاموش‌بودنِ همان بهبود است ✓ (قاعدۀ ۹.۶: نمادِ مطمئن‌نشده را با رشته بگو یا نگو ✓).

**چرا:** پنج bullet اول هر کدام یک «شکستِ بی‌صدا» را می‌بندند: رویدادِ بی‌مصرف‌کننده در enumِ تازه ✗،
